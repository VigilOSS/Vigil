# CODE-MAP

This file is the repo's stable structure map.

Use it to answer:
- Where does this concern live?
- Which file owns the contract?
- Which generated files must stay in sync?

Keep it light:
- Track stable boundaries, entrypoints, ownership, and sync relationships.
- Omit caches, vendor trees, generated build output, and field-level trivia.
- If a change makes any statement here false, update this file in the same change.
- Do not churn this file for implementation-only edits that do not move a boundary.

## Root

- `README.md` - operator/install guide. Why: defines the supported runtime model and engagement startup flow.
- `AGENTS.md` - maintainer workflow. Why: the clone-to-first-dispatch newcomer walkthrough, the "add a skill / `vigil assess` verb / oracle / eval case" recipes, local development rules, verification steps, and prompt regeneration requirements live here.
- `pyproject.toml` and `src/vigil_cli/` - universal CLI package. Why: `vigil` / `vigil` owns install/update, config, doctor/status, centralized logs, engagement creation/listing/selection (including Android APK artifact-only scope creation, blue incident engagement scaffolding through `vigil blue`, and per-engagement Codex/Claude roster links), all-up local stack startup via `vigil up`, orchestrator lifecycle, Kali runtime lifecycle (including resource-tier env vars and the `vigil runtime resources` introspection subcommand), non-interactive `runtime shell-exec`, mitmproxy capture startup, OOB/frp/interactsh control, backup/auth helpers, and `vigil assess` pass-through. The Wave 1 cutover (2026-04-26) replaced Kali MCP with `vigil assess kali` host-side subcommands; `vigil mcp install/status/remove/repair` is a deprecation stub that exits 2 with a pointer at the new vocabulary.
- `docker/callback_listener.py` and `docker/start-callback.sh` - optional callback sink. Why: support OOB and exploit validation outside the main orchestrator path.

## agent/

### Prompt system

- `agent/operator-core.md` - primary operator loop for web/runtime engagements. Why: phase order, dispatch rules, recording rules, and backend-vs-artifact truth boundaries start here.
- `agent/operator-core-blue.md` - operator loop for blue-team incident response engagements. Why: intake/triage/investigate/verify/respond/report phase gates, `vigil blue` wrapper usage, containment approval/recording rules, and tenant-reference injection start here.
- `agent/operator-core-code.md` - operator loop for white-box code analysis. Why: same backend and CLI, different phase model.
- `agent/shared-constraints.md`, `agent/shared-constraints-code.md`, and `agent/shared-constraints-blue.md` - first-load specialist constraints. Why: global safety, scope, output rules, and mode-specific audit/tenant rules live outside individual agent prompts.
- `agent/rules/` - always-active policy overlays. Why: resume hydration plus hunting/reporting/adversarial guardrails apply across prompts.
- `agent/agents/` - canonical specialist prompt sources. Why: role-specific behavior belongs here, not in generated wrappers.
- `ENGAGEMENT.md` (per-engagement) and `scope.json` - per-engagement ROE and machine-enforced scope. Why: engagement-specific rules of behavior (no-fire endpoints, required headers, rate caps, exfiltration limits) belong here and never enter operator-core or shared-constraints. The four prompt altitudes: global behavior → `operator-core.md`; all-specialist safety → `shared-constraints*.md`; per-engagement ROE → `ENGAGEMENT.md`; machine-enforced scope → `scope.json`.

### Skill and reference library

- `agent/SKILL.md` - **deprecated** roster of the procedure layer; superseded by `vigil assess list-skills`. Why: keep the file as a soft pointer for older operators, but discovery should walk `agent/skills/*/SKILL.md` frontmatter directly so a new skill is visible the moment its directory exists, with no roster edit required.
- `agent/skills/` - procedure layer. Why: workflow and vuln-family methodology lives here. `agent/skills/kali-exec/SKILL.md` is the discovery anchor for the `vigil assess kali` CLI surface; per-verb references live under `agent/references/tools/`.
- `agent/references/` - methodology library, discovered via `vigil assess list-references` (self-registering frontmatter, no index file to maintain — mirrors `list-skills`). Why: payloads, checklists, tool notes, and code-vuln patterns are loaded on demand from here.
- `agent/references/gf-patterns/` - per-bucket gf-pattern reference files (one `.md` per bucket: `ssrf`, `idor`, `sqli`, `lfi`, `rce`, `xss`, `ssti`, `redirect`, `debug_logic`, `cors`, `upload_fields`, `trust_surface`, `img_traversal`, `interestingparams`, `interestingsubs`, `interestingEXT`). Why: `agent/skills/gau-triage/SKILL.md` and the inline classifier load these on demand instead of inlining pattern explanations, so classification guidance stays modular as buckets are added or tuned.
- `agent/references/gf-patterns/DRIFT.md` - static accept/skip rationale for GF categories that do not map directly to Python buckets. Why: upstream GF buckets rarely change; keeping the curated rationale beside the bucket references is simpler than maintaining a sync script and vendored JSON cache.

### Generated prompt outputs

- `agent/scripts/render-operator-prompts.sh` - prompt renderer. Why: generates committed red wrappers from `operator-core.md` and blue wrappers from `operator-core-blue.md` for all three runtimes — Claude (`.claude/agents/*.md`), Codex (`.codex/agents/*.toml`), and OpenCode (`.opencode/agent/*.md`); source-tree `agent/AGENTS.md` remains the canonical red rendered operator prompt, while per-blue-engagement `AGENTS.md` is rendered into that engagement directory with `--type blue`. `agent/CLAUDE.md` is intentionally a one-line pointer to `AGENTS.md` so Claude Code does not load the same operator instructions twice. The OpenCode wrappers pin a per-role `model` (`agent_model`: `deepseek/deepseek-v4-pro` for the operator + hard exploit/analysis/verification/synthesis roles, `deepseek/deepseek-v4-flash` for bounded recon/parse/enumeration sweeps) because OpenCode subagents otherwise inherit the invoking primary's model.
- `agent/AGENTS.md` - generated canonical operator wrapper. Why: committed output, not a source-of-truth.
- `agent/CLAUDE.md` - thin pointer to `AGENTS.md`. Why: token deduplication for Claude Code, which auto-loads both files when present.
- `.cursor/rules/operator.md` - Cursor-specific rule that prevents `CLAUDE.md` from being loaded alongside `AGENTS.md`. Why: same deduplication concern, scoped to the Cursor IDE.
- `agent/.codex/config.toml` - Codex project hook config. Why: wires Codex `PreToolUse`/`PostToolUse` events to the shared hook scripts.
- `agent/.codex/agents/` and `agent/.claude/agents/` - generated agent definitions. Why: client-specific committed outputs embed canonical specialist prompt bodies from `agent/agents/*.md`; edit source prompts and rerender instead of editing these directly.

- `agent/scripts/assess/lib/` - shared plumbing. Why: API client (`client.py`), bulk assessment ingestion transport (`bulk_ingest.py` — shared `/request-observations/bulk` and `/coverage-items/bulk` client helpers with compatibility fallback for older backends), helper contract metadata (`contracts.py` — owns the `kali` root + per-verb contracts, the split `KALI_TARGET_VERBS`/`KALI_MAINT_VERBS` rosters (`KALI_VERBS` is the union for registration), agent/work-buffer contract text, and `validate_specialist_dispatch_contract` which requires `skills` for non-operator roles; `schema.sql` deliberately does NOT define this view), the candidate metadata column migration, the inline call into `classify_buckets.classify_from_fields()` (which builds a synthetic row and delegates to `classify_row`) so `db_insert_work_item()` populates `priority_score`/`priority_reason`/`cluster_key`/`terminal_reason` at ingest time, and curated rekey/update semantics for metadata-preserving candidate rows; re-exports `INERT_TYPES` as `_SKIP_TYPES` so the inline insert path skips inert rows from the same set the bucket classifier uses), `candidate_records.py` (single parser/classifier for curated candidate JSONL consumed by `ingest-candidates`), `classify_buckets.py` (single source of truth for the gf-style URL `_BUCKETS` table, the public `INERT_TYPES` frozenset, AND the `SKIP_REASON_TAGS` taxonomy + `tagged_terminal_reason`/`reason_tag_of` helpers that de-overload the `skipped` terminal state — `defer-cluster --reason-tag` stamps `terminal_reason` as `skipped:<tag> | <text>` and `work-buffer stats --by reason` surfaces `untagged` drops; Split for blast-radius minimization across:

  - **`kali_audit.py`** — pre-exec `command-runs` POST, finalize PATCH, failed-audit marker, input validation, agent-name + engagement-dir resolution.
  - **`kali_runtime_exec.py`** — `_build_docker_exec` wrapper-shell construction (passes `--env ENGAGEMENT_KEY=<key>` so skill examples like `nuclei -l /engagements/$ENGAGEMENT_KEY/...` expand inside the container; the same env is mirrored in `kali_jobs.py` `dtach_argv`), `_check_container_running`, `_read_container_pid` / `_kill_in_container` / `_cleanup_container_pid_file` (the exact-PID two-namespace kill cascade primitives).

  - **`kali_tool_naming.py`** — `_derive_tool_name`, `_analyze_tool_name`, and the shell-pipeline parsing helpers (pure functions; no I/O).
  - **`kali_cli.py`** — argparse scaffolding (`add_required_kali_flags`, `add_passthrough_args_flag`, `extend_cmd_with_extra_args`, `kali_args_to_kwargs`, `emit_result`) shared by every `kali_<verb>` command file.
  - **`kali_jobs.py`** — async-job lifecycle helpers (`start_job`, `job_status`, `job_tail`, `job_stop`, `job_list`) for the dtach-supervised SQLite-backed job worker. The dtach wrapper redirects the in-container command's stdin from `/dev/null` so a backgrounded ProjectDiscovery tool (httpx/katana/nuclei/dnsx/naabu) cannot block on a non-EOF stdin — the in-container analogue of the synchronous exec path's `stdin=DEVNULL`.
- `agent/scripts/assess/lib/reachability.py` + `discovery.py` - pure helpers shared by the discovery pipelines and `ingest-httpx`. `reachability.classify_probe()` is the single source of truth for the per-host reachability verdict (`live` / `blackholed` / `tls13_reset_recover_with_12` / `unknown`); it encodes the §9 lesson that a bare `connect=000` / `http_code=000` is NOT a blanket "blocked" (it can be a CONNECT-proxy artifact or a TLS-1.3 reset), so a verdict requires no TCP connect AND no resolved IP. `discovery.denoise_hosts()` is the single source of truth for the PTR/MAC/DHCP/service-record noise filter the subdomain-enumeration skill documents.
- `agent/schemas/` - JSON payload contracts. Why: durable record formats for findings, intel, chains, credentials, access records, probe runs, proposals, and code-analysis outputs live here; backend-backed schemas are generated from backend request models plus explicit agent-side overlays, while `session-proposal.schema.json` remains local because it has no backend model.
- `agent/scripts/schema.sql` - transient local queue schema. Why: local case/work-item buffering, not orchestrator backend state. `work_items` carries triage columns (`priority_score`, `priority_reason`, `cluster_key`, `terminal_reason`) plus curated candidate metadata (`signals`, `selected_by`, `triage_rationale`, `live_status`) and a `(status, priority_score DESC, cluster_key)` index that power signal-first dispatch; `agent/scripts/assess/lib/db.py` runs `_apply_work_items_priority_migration` on open so existing engagement DBs self-upgrade. The file deliberately defines tables/indexes only — the `work_items_per_host` view is owned by `db.py:_apply_work_items_per_host_view` so legacy and fresh DBs end up with the same DDL (no two-place drift). Fresh engagements get the view because `src/vigil_cli/engagements.py:_init_cases_db` calls `db_init()` rather than running `executescript(schema.sql)` directly.
- `agent/scripts/proxy_addon.py` - mitmproxy collector. Why: converts captured traffic into the transient work buffer through the shared `db_init()` / `db_insert_work_item()` path, so browser-captured rows receive the same schema migrations and inline classification as `ingest-endpoints` and `ingest-spec`. Multi-engagement aware: one proxy container holds an in-memory registry of every active engagement (sourced from `GET /engagements?status=in_progress`, filesystem scan of `agent/engagements/*/scope.json` as fallback, refreshed every 30 s and on demand via the `.mitmproxy-reload-requested` sentinel). Per-flow routing picks the best engagement by precedence — literal-host > narrower wildcard > `scope_priority` > most-recently-updated — and routes captured-credential POSTs (to the backend credential store, `default` identity), cases.db inserts, and `/engagements/<key>/assessment/request-observations` POSTs to that engagement only.
- `src/vigil_cli/engagements.py`, `src/vigil_cli/blue.py`, and `src/vigil_cli/client_rosters.py` - engagement bootstrap. Why: creates run directories, seeds local wrappers plus engagement-local `.codex/agents`, `.claude/agents`, and `.opencode/agent` links to generated specialist wrappers, renders blue per-engagement prompts with `render-operator-prompts.sh repo <eng_dir> --type blue`, copies Claude settings and the standard OpenCode plugin (`_write_opencode_config`: copies `agent/.opencode/plugin/standard-hooks.js` — scope-check in `tool.execute.before`, post-tool-log in `tool.execute.after` — into the engagement's `.opencode/plugin` + `.opencode/plugins`, installed for every kind that also gets `start_opencode.sh`) when present, initializes scope/auth/runtime scaffolding, including Android `scope_mode: artifact-only` engagements with APK/AAB/XAPK artifacts kept out of `hosts` and blue `engagement_type=blue` incident scopes with tenant references, and exposes list/path/start/blue helpers for universal `vigil` use. The durable blue CLI surface includes customer discovery (`vigil blue customers`), engagement creation (`vigil blue engage`), operator-chat alert recording (`vigil blue alert record`), specialist dispatch/verify/containment wrappers, containment recording linked to a proof artifact or audited command-run id, and final closeout/report dispatch (`vigil blue closeout` / `vigil blue report`). `_init_cases_db` delegates to `agent/scripts/assess/lib/db.py:db_init` (rather than running `executescript(schema.sql)` directly) so a fresh engagement DB ends up with the same schema, priority-column migration, AND `work_items_per_host` view as one created via the assess CLI — the DB-init path is the single seam that owns "what a cases.db looks like." Also owns the one-shot `migrate_legacy_both_engagements()` helper exposed as `vigil engagement migrate-scope`, which back-fills `code_phase=ingest` on legacy `engagement_type=both` engagements created before dual-track phase tracking; `vigil status` calls `_both_engagements_missing_code_phase()` to surface a warning line when any such engagement remains unmigrated.
- `src/vigil_cli/runtime.py`, `src/vigil_cli/up.py`, and the runtime subcommands in `src/vigil_cli/main.py` - shared runtime bootstrap and execution. Why: starts and validates the canonical Kali container with explicit Docker resource flags (`--memory`, `--cpus`, `--pids-limit`, `--shm-size`, `--ulimit nofile/nproc`, `--oom-score-adj=-500`) sourced from `VIGIL_RUNTIME_*` env vars (`MEMORY_GB`, `CPUS`, `PIDS_LIMIT`, `SHM_SIZE`); compares image-ID drift against the configured image tag; exposes `vigil runtime shell-exec` (host-initiated runtime commands) and `vigil runtime resources` (prints configured tier + live cgroup state); coordinates all-up local stack startup (`runtime`, stale Docker image builds, mitmproxy, OOB, and orchestrator) without restarting existing OOB tmux sessions. Bind-mounts `$INSTALL_ROOT/agent/engagements` at `/engagements` inside Kali (alongside the shared `/data` mount) so skills can reach engagement artifacts at `/engagements/$ENGAGEMENT_KEY/...` without ferrying files across the container boundary. The Kali container is reached host-side via `docker exec` from `agent/scripts/assess/lib/kali.py` — there is no longer an in-container HTTP API server or MCP stdio bridge.
- `src/vigil_cli/orchestrator.py` - local UI/backend lifecycle. Why: builds the frontend when needed and manages the backend process on `127.0.0.1:18000`.
- `src/vigil_cli/bench/` - **`vigil bench`** benchmark harness. Why: runs procedurally-generated families (or any provider) against the unmodified Vigil agent to measure partial-credit chain depth (generated) or flag-capture solve-rate (non-generated) by vuln class × difficulty. Provider-agnostic (`providers.py`: `GeneratedProvider` renders families on demand; `SelfTestProvider` is a synthetic flag-on-root target for pipeline checks; XBEN was retired — see ADR 0002). Enforces two guarantees: no cheating (random per-run flag injected as a docker build-arg, target isolated on a per-attempt `--internal` docker network reachable only from the shared Kali via a neutral `target-<hex>` alias, an additive `bench-guard.sh` PreToolUse hook, and a post-run `taint.py` audit of `assessment_command_runs`/activity that disqualifies a flag obtained via host docker/curl/mount reads) and no recognition (every observable identifier — alias, engagement key, URL, task text — is neutral; the neutral-id↔vuln-class↔flag answer key lives only in the off-tree judge manifest under `$VIGIL_BENCH_HOME`, default `~/.vigil-bench`, never in the repo or an engagement dir). Verbs: `list/run/commands/score/teardown/selftest/history`. `run --launch manual` (default) stages targets and prints the human launch command (interactive `start_<client>.sh "<ctf-msg>"`, not `claude -p`); `--launch auto` spawns the real client (`--client claude`/`codex`/`opencode`/`goose`; `goose` is the PRIMARY open-model client — it dispatches custom specialist subagents headless via `delegate source <role>` (`.goose/recipes/*.yaml`) AND its `PreToolUse` anti-cheat hook fires inside subagents, unlike `opencode`; runs direct DeepSeek as the non-thinking `deepseek-chat` (thinking-mode V4 breaks on goose's openai provider, #9397), wired by `engagements._write_goose_config` (`.goosehints` + recipe link + `vigil-standard` hooks) and `anticheat._patch_goose_hooks` (`vigil-bench` guard via `goose-hook-adapter.sh`) — see `docs/goose-bench.md`. `opencode` drives DeepSeek direct via the generated `start_opencode.sh` → `opencode run`. Anti-cheat layers exactly like Claude/Codex: the standard OpenCode plugin (`standard-hooks.js`, installed by `create_engagement` → `_write_opencode_config`, owns scope-check + `post-tool-log.sh` activity logging) plus a guard-only `bench-guard.js` the bench writes beside it (`anticheat._patch_opencode_plugin`, owns `bench-guard.sh` blocking) — so a bench opencode engagement keeps BOTH blocking and logging without double-logging; see `docs/deepseek-openrouter.md`); `--launch scripted` (and `selftest`) drive a synthetic agent with no LLM. Reuses `engagements.create_engagement`, `docker.py`, `runtime_resources`/`docker_info` for concurrency sizing, and `assess.lib.client.AssessmentClient` for findings/command-run readback. Per-attempt isolation (own network/alias/project/engagement) over one shared Kali + one backend; `VIGIL_RUNTIME_CONTAINER` is the per-worker-Kali escape hatch if shared `/data` contention appears. **Bench v2 (generated suite):** `--provider generated` adds a procedural hard/very-hard track scored by a step-DAG partial-credit oracle instead of binary flag capture. `bench/factory/` (`render`/`axes`/`rename`/`inject`/`verify` + `oracle_lib/checkpoint.py` COPYed into target images) deterministically materializes a multi-container FastAPI source_dir per `(family, seed)`; families live in `bench/factory/families/<id>/` (`family.yaml`/`dag.yaml`/`injection.yaml`/`skeleton/`/`solve.py.j2`) — currently `bola-rest-graph`, `ssrf-imds-chain`, `jwt-confusion-bola`. The app emits checkpoint events on **real privileged state** to an isolated Docker named volume (`oracle-log`, never bind-mounted to host/Kali); `bench/oracle.py` (`load_dag`/`collect`/`score`) reads it host-side post-run and computes topo-prereq-gated severity-weighted partial credit (an in-app `decoy_tripped` PROBE event is reported separately as a **near-misses-probed** signal — enumeration thoroughness, NOT a penalty — and never subtracted from the score; see ADR 0003). A SEPARATE, orthogonal **finding-precision / FP-discipline axis** (ADR 0003 Alternative #2) answers a different question — did the agent *record a finding* that targets a honeypot route? Route-class decoys carry `route:` in `dag.yaml`; `factory/render.py._resolve_decoy_routes` resolves them through the per-seed rename context into a host-side `.oracle/decoys.json` answer key (`.dockerignore`-excluded, deterministic per `(family,seed)`); `oracle.load_decoy_routes`/`attribute_findings_to_decoys`/`finding_precision` (pure) match a recorded finding's URL path against each attributable decoy and compute `precision = true/(true+decoy)` (behavioral SSRF decoys are `attributable:false`; agent-dismissed findings are excluded). `lifecycle.score()` populates `AttemptResult.finding_precision`/`decoy_findings`; `scoring.py` surfaces per-instance/family/suite `mean_precision` + an FP count. This axis NEVER enters `partial_credit`/`_scored_partial_credit`/`pass@k`. `GeneratedProvider` + `staging.stage()` multi-service connect (`StagedTarget.additional_services`) + the oracle block in `lifecycle.score()` are all additive and guarded on `spec.is_generated`, so the non-generated flag/matrix path is byte-for-byte unchanged; generated runs render a dedicated partial-credit progress table (`scoring.py`). `factory/verify.py` is the quality gate — it builds + runs each seed's reference `solve.py` and asserts the oracle reaches max severity (the challenge is solvable + correctly instrumented) plus a render-determinism check. ### Anti-patterns flagged by review

These came up during the mid-engagement review and the consolidation work above. Read them before adding a new "small" invariant copy:

- **Hardcoded SQL `IN ('image', ...)`**: build the placeholders from `INERT_TYPES` (see `classify_work.py` for the pattern). Hand-typed inert sets in SQL are the most-frequent drift class in the codebase history.
- **"Almost-the-same" verb tuples**: don't fork `KALI_VERBS` into a target-facing-only copy by hand. Add to `KALI_TARGET_VERBS` or `KALI_MAINT_VERBS` and recompose.
- **Help-string verb lists**: build with `', '.join(_TUPLE)`. Hand-typed argparse help that lists actions ages out within a release.
- **"Looks like a schema, isn't a schema"**: `agent/scripts/schema.sql` only owns CREATE TABLE / CREATE INDEX. Views and runtime migrations live in `db.py` so legacy DBs catch up on every `db_init`.
- **Operator reading skills**: skills are dispatched-to, not read by the operator (see `operator-core.md` step 5). The `--skills` flag exists for audit; the dispatch prompt carries the `path` for the specialist to load.
- **Editing generated wrappers**: never edit `agent/AGENTS.md`, `agent/CLAUDE.md`, or anything under `.claude/agents/` / `.codex/agents/` / `.opencode/agent/` / `.goose/recipes/`. They open with a `GENERATED FILE — DO NOT EDIT` banner; edit the source under `agent/operator-core.md` or `agent/agents/*.md` and run `agent/scripts/render-operator-prompts.sh repo`.

Flags: `--phase` (required), `--depth`/`--by-app-unit`, `--by-host`, `--auto-redispatch`, `--strict` (CI exit-1 on open advisory; preserves old intel `--strict`), `--strict-deep` (gate on app-unit detection, default OFF), `--include-intel`, `--json`. The terminal report/complete hard block is INDEPENDENT of `--strict`/`--strict-deep` (it lives on the `transition-phase` precondition).
- **Backend phase-readiness module:** `orchestrator/backend/app/services/state_manager/phase_readiness.py` exposes `phase_readiness(engagement_id, phase)`, served at `GET /engagements/{key}/assessment/phase-readiness?phase=…` (`api/assessment.py:get_phase_readiness`). It ASSEMBLES per-phase results by CALLING the existing, UNCHANGED gates — `coverage_readiness` / `report_readiness` / `per_host_coverage` / `depth_ledger` / intel `intel_readiness`. **Those four state-manager function names AND the HTTP routes `/coverage-readiness`, `/coverage-readiness/by-host`, `/report-readiness` are STABLE** (the phase-transition gate, `report_export`, `assessment_summary`, and the frontend bind to them) — refactor BEHIND them, never rename them. `phase_readiness` is additive-only.
- The scope gate reads durable state directly (`GET /services`, `GET /surfaces`, local `work_items`) — no per-tool registry or argv-parsing layer. A scope entry "enumerated" when a live service, surface, or work item exists under it; "collected" when a surface or work item exists under it. If a tool should feed the gate, make sure its output lands in services/surfaces/work_items (via `record-surface`, `ingest-endpoints`, etc.). The per-scope-entry logic + helpers (`_load_work_items_by_host`, `_consumption_satisfied`, `build_scope_coverage_report`, the `--auto-redispatch` machinery) are in `lib/coverage_checks.py`; extend `orchestrator/backend/tests/test_check_scope_coverage.py` for new fixtures.
- `state_manager._derive_tool_bin` still shell-parses command strings for audit/UI filtering (Commands tab), not for coverage. Wrapper-stripping changes there are independent of the scope-coverage gate.
- C40 per-host outcome audit: `vigil assess check-phase-readiness --phase recon|collect|consume --by-host` calls `GET /coverage-readiness/by-host`, owned by `state_manager.per_host_coverage`. The projection reads outcome tables only (`intel_tech_components`, `intel_people`, `intel_breach_records`, `assessment_services`, `assessment_surfaces`, `assessment_dispatch_decisions`) — explicitly NOT `assessment_command_runs`. `orchestrator/backend/tests/test_per_host_coverage.py` enforces the abstraction via a monkeypatched `get_connection` spy. The audit is WARN-only; missing objectives never block phase advance. Operators record intentional skips via `vigil assess agent decision --kind coverage_deferral --payload-json '{"host": "...", "deferred_objectives": ["..."], "reason": "..."}' --surfaced-to-user`. The five objectives — `waf_tier`, `service_inventory`, `directory_fuzz`, `tech_fingerprint`, `osint` — are listed in `state_manager.PER_HOST_OBJECTIVES`, the CLI's mirror tuple in `lib/coverage_checks.py:_PER_HOST_OBJECTIVES`, and the `_COVERAGE_DEFERRAL_OBJECTIVES` tuple + `coverage_deferral` `deferred_objectives` Literal in `assessment.py`; keep them in sync. (`tech_fingerprint` is satisfied by ANY tech/server-fingerprint source — whatweb/httpx/wappalyzer/nuclei/nmap/nikto/manual intel — it is NOT a nikto-specific gate; the matrix column is labeled "Tech fingerprint".)
- WAF family tokens and tech-scan source tokens in `state_manager._WAF_FAMILY_TOKENS` / `_TECH_SCAN_SOURCE_TOKENS` are matched as substrings against `intel_tech_components.component` and `source_name` respectively. Adding a new CDN entrant is an additive edit; the abstraction does not need to learn the tool that produced the row.

When adding new patchable code-analysis fields or structural metadata totals:
- Update the backend schema in `orchestrator/backend/app/db.py`, the API layer in `orchestrator/backend/app/api/code_analysis.py`, and the service-layer allowlists in `orchestrator/backend/app/services/code_analysis.py` together. `update_code_repo`, `update_code_file`, and `bulk_update_structural_metadata` only persist fields that appear in their hard-coded allowlists/field sets; new columns are now rejected loudly at the PATCH/sync layer until those registration points are updated.
- If the field is populated from tree-sitter output, also update `agent/scripts/assess/commands/code_index_sync.py` and the `CODE-MAP.md` sync note for structural metadata so index artifacts and backend storage stay aligned.

## Update Triggers

Update this file when a change does any of the following:
- adds, removes, renames, or moves a stable entrypoint;
- changes which file owns a contract or boundary;
- changes a generation or sync relationship;
- adds or removes a durable API/service/tab/CLI command family;
- changes which directory is the canonical home for a concern;
- touches a drift-prone depth-harness invariant (the canonical vuln taxonomy / app-framework token set / scorer weights+thresholds / `result_status` covering vocabulary / the §5.3 Expected-class predicate table) — these are data-driven and dated specifically so they age gracefully; adding a framework, class, or outcome value must be an ADDITIVE edit to the list, never a control-flow change, and the drift tests (`test_vuln_taxonomy.py`) must stay green so a newly-added skill/bucket that isn't wired fails CI instead of silently widening the blind spot;
- renames/moves a readiness gate — the function names `coverage_readiness` / `report_readiness` / `per_host_coverage` / `depth_ledger` and the HTTP routes `/coverage-readiness`, `/coverage-readiness/by-host`, `/report-readiness` are load-bearing (phase-transition gate, `report_export`, frontend) and must stay stable; add a new front door (like `phase_readiness`) that CALLS them instead.

Do not update this file for:
- implementation-only edits inside an unchanged boundary;
- temporary experiments, caches, or local machine state;
- field additions that do not create a new durable boundary.
