# CODE-MAP

This file is the repo's stable structure map.

Use it to answer:
- Where does this concern live?
- Which file owns the contract?
- Which generated files must stay in sync?

Keep it light:
- Track stable boundaries, entrypoints, ownership, and sync relationships.
- Omit caches, vendor trees, generated build output, and field-level trivia.
- If a change makes any statement here false, update this file in the same change.
- Do not churn this file for implementation-only edits that do not move a boundary.

## Root

- `README.md` - operator/install guide. Why: defines the supported runtime model and engagement startup flow.
- `AGENTS.md` - maintainer workflow. Why: the clone-to-first-dispatch newcomer walkthrough, the "add a skill / `vigil assess` verb / oracle / eval case" recipes, local development rules, verification steps, and prompt regeneration requirements live here.
- `CLAUDE.md` - source-checkout entrypoint pointing contributors to root `AGENTS.md`. Why: repository maintenance must not implicitly assume the engagement operator role; engagement sessions use their own local entrypoints.
- `pyproject.toml` and `src/vigil_cli/` - universal CLI package. Why: `vigil` / `vigil` owns install/update, config, doctor/status, centralized logs, engagement creation/listing/selection and explicit scope/track mutation (`engagement add-track|repair-tracks|add-host|set-rate-limit`, including Android APK artifact-only scope creation, blue incident engagement scaffolding through `vigil blue`, and per-engagement Codex/Claude roster links), all-up local stack startup via `vigil up`, orchestrator lifecycle, Kali runtime lifecycle (including resource-tier env vars and the `vigil runtime resources` introspection subcommand), non-interactive `runtime shell-exec`, mitmproxy capture startup, OOB/frp/interactsh control, backup/auth helpers, and `vigil assess` pass-through. The 2026-04-26 cutover replaced Kali MCP with `vigil assess kali` host-side subcommands; the `vigil mcp` deprecation stub was removed entirely in the 2026-07 CLI consolidation.
- `docker/callback_listener.py` and `docker/start-callback.sh` - optional callback sink. Why: support OOB and exploit validation outside the main orchestrator path.

## agent/

### Prompt system

- `agent/operator-core.md` - primary operator loop for web/runtime engagements. Why: phase order, dispatch rules, recording rules, and backend-vs-artifact truth boundaries start here.
- `agent/operator-core-blue.md` - operator loop for blue-team incident response engagements. Why: intake/triage/investigate/verify/respond/report phase gates, `vigil blue` wrapper usage, containment approval/recording rules, and tenant-reference injection start here.
- `agent/operator-core-code.md` - operator loop for white-box code analysis. Why: same backend and CLI, different phase model.
- `agent/shared-constraints.md`, `agent/shared-constraints-code.md`, and `agent/shared-constraints-blue.md` - first-load specialist constraints. Why: global safety, scope, output rules, and mode-specific audit/tenant rules live outside individual agent prompts.
- `agent/rules/` - always-active policy overlays. Why: resume hydration plus hunting/reporting/adversarial guardrails apply across prompts.
- `agent/agents/` - canonical specialist prompt sources. Why: role-specific behavior belongs here, not in generated wrappers.
- `ENGAGEMENT.md` (per-engagement) and `scope.json` - per-engagement ROE and the machine-readable scope declaration. Why: engagement-specific rules of behavior (required headers, rate caps, exfiltration limits) belong here and never enter operator-core or shared-constraints. `scope.json` `hosts` declares the original authorization roots and is read by host-set-shaping surfaces (recon/ingest filtering, proxy flow ownership, and coverage accounting), never by outbound or dispatch admission. The composed and standalone discovery pipelines merge confirmed children of an original wildcard into the derived `discovered_hosts` inventory without changing `hosts`; scope matchers intentionally ignore that inventory. Staying inside the original roots is the operator's and specialist's responsibility. The four prompt altitudes: global behavior → `operator-core.md`; all-specialist safety → `shared-constraints*.md`; per-engagement ROE → `ENGAGEMENT.md`; machine-readable scope declaration → `scope.json`.

### Skill and reference library

- `agent/SKILL.md` - **deprecated** roster of the procedure layer; superseded by `vigil assess list-skills`. Why: keep the file as a soft pointer for older operators, but discovery should walk `agent/skills/*/SKILL.md` frontmatter directly so a new skill is visible the moment its directory exists, with no roster edit required.
- `agent/skills/` - procedure layer. Why: workflow and vuln-family methodology lives here. `agent/skills/kali-exec/SKILL.md` is the discovery anchor for the `vigil assess kali` CLI surface; per-verb references live under `agent/references/tools/`.
- `agent/references/` - methodology library, discovered via `vigil assess list-references` (self-registering frontmatter, no index file to maintain — mirrors `list-skills`). Why: payloads, checklists, tool notes, and code-vuln patterns are loaded on demand from here.
- `agent/references/gf-patterns/` - per-bucket gf-pattern reference files (one `.md` per bucket: `ssrf`, `idor`, `sqli`, `lfi`, `rce`, `xss`, `ssti`, `redirect`, `debug_logic`, `cors`, `upload_fields`, `trust_surface`, `img_traversal`, `interestingparams`, `interestingsubs`, `interestingEXT`). Why: `agent/skills/gau-triage/SKILL.md` and the inline classifier load these on demand instead of inlining pattern explanations, so classification guidance stays modular as buckets are added or tuned.
- `agent/references/gf-patterns/DRIFT.md` - static accept/skip rationale for GF categories that do not map directly to Python buckets. Why: upstream GF buckets rarely change; keeping the curated rationale beside the bucket references is simpler than maintaining a sync script and vendored JSON cache.
- `agent/references/reporting/` - severity/taxonomy lookup tables for report writing: `bugcrowd-vrt.{tsv,md}` (Bugcrowd VRT priority + CVSS-v3, pinned to a tagged upstream release) and `hackerone-weaknesses.{tsv,md}` (HackerOne CWE/CAPEC-based weakness taxonomy, severity-free by design, with CWE Top-25 flag). Why: report-writer skills look up the exact VRT path / H1 weakness name here instead of guessing. Each `.tsv` is regenerated by its own tool — `tools/flatten_vrt.py` and `tools/fetch_hackerone_weaknesses.py` (offline-first: embeds a last-known-good snapshot and falls back to it on any fetch failure) — and the `.md` is a human-readable render of the same data. These replace the old root-level `bugcrowd-vrt-lookup.*` files, which are deleted.

### Runtime and CLI

- **Connectivity and WAF observation persistence.** `agent/scripts/assess/commands/egress_check.py` records observed cluster blackholes, failed controls, and incompletely classified samples as advisory `egress_decision` rows with exact classifications, reason/provenance, and an indexed probe artifact; a failed control is explicitly inconclusive. `agent/scripts/assess/lib/kali.py:_record_waf_observation` persists an already-detected WAF challenge after command-run finalization with its detector reason, command provenance, and retained stdout reference. Both use the existing audit-UI-visible `egress_decision` family and distinguish `connectivity_check` from `waf_challenge` in `payload.subtype`; neither path adds probing, retry, cooldown, gating, or dispatch behavior.

- `agent/scripts/assess.py` - `vigil assess` implementation entrypoint. Why: stable helper surface into the assessment and code-analysis workflows.
- `agent/scripts/assess/cli.py` - subcommand registry. Why: authoritative map of supported operator/backend actions, including the `kali` subgroup that owns target-facing tool execution and `list-skills` for skill discovery from `agent/skills/*/SKILL.md` frontmatter.

Why: `vigil assess fixture observe|resolve` records concrete IDs from an observed response and resolves rotation-safe manifest aliases without storing credentials; contract metadata lives in `agent/scripts/assess/lib/contracts.py`.
- `agent/scripts/assess/commands/proof_run.py` + `agent/scripts/assess/commands/run_audit.py` - shared run-accounting CLI boundary. Why: `proof-run` creates, starts, seals, resumes, and reads generic proof/scan runs; `run-audit` publishes exact inventories, debt/candidate decisions, typed tool signals, attributed discovery passes, and generation-bound links to the existing variant/fuzz receipt owners. It is also the only source-read verb that proves delivery by safely opening the inventoried rooted path, streaming exact bytes, verifying size/digest, and then recording derived byte/line ranges. Ordinary lists are bounded and explicit `--paginate` traverses all pages.
- `agent/scripts/assess/commands/prompt_census.py` + `agent/scripts/assess/lib/prompt_census.py` - non-blocking prompt measurement boundary. Why: `vigil assess prompt-census` reports expected authored sections, Load-First structure, file bytes, and optional observed-read bytes without making Markdown wording or line positions executable contracts.
- `agent/scripts/assess/commands/export_triage_packet.py` - canonical blind-triage packet assembler. Why: `vigil assess export triage-packet` reads the exact existing submission, engagement brief, and blind-triage rubric through no-follow descriptors, publishes a content-addressed immutable packet with a digest manifest, and declares that it does not provide participant/process isolation; it never re-renders the submission.
- `agent/scripts/assess/commands/` - command families. Why: fetch/post/patch, finding/surface/intel lifecycle helpers (including `finding relocate`, the typed compare-and-swap surface for audited canonical-location moves and terminal-verification invalidation), helper contract introspection, backend agent lifecycle (`agent start|done|list|get|handoff|render-handoff|decision|close|reconcile-stale`), engagement resume (`resume-brief`), artifact index search/get/register/refresh (`artifact`), backend work-buffer operations (`work-buffer fetch|fetch-by-unit|done|error|reset-stale|retry-errors|defer-*|set-rationale|requeue|stats` over `assessment_work_items` — ADR 0013; `defer-* --dry-run` previews exact pending matches, `stats --by host --status` narrows queue censuses, and `fetch-by-unit` atomically selects one highest-EV/explicit application unit and claims its routed rows with literal path/class narrowing and depth/saturation batch sizing), curated ingestion (`vigil assess ingest <candidates|endpoints|spec|arjun|httpx>` — one grouped verb; `ingest candidates`/`ingest endpoints`/`ingest spec` batch high-volume backend request-observation writes and carry a `work_item` derivation block the backend persists into `assessment_work_items` in the SAME transaction, no separate insert step; `ingest arjun` folds Arjun hidden-param discovery into the buffer; `ingest httpx` parses httpx `-json` into the backend `assessment_host_liveness` ledger), composable discovery pipelines (`dns-discovery` = subfinder+CT+optional-brute → merge/de-noise → dnsx-resolve; `web-discovery` = de-noise → httpx liveness → auto-ingest the liveness ledger → katana crawl → optional work-buffer ingest; each run writes under `scans/<pipeline>/runs/<run-id>/`, and only an accepted complete/accepted-empty generation promotes canonical intermediates and finals; standalone web host-set shaping uses the shared exact-host/wildcard/deny/bypass scope policy), `egress-check` (samples in-scope hosts + a known-good control via the shared reachability verdict and records an advisory `egress_decision` when the cluster is blackholed but controls connect — §9), cache-aware gau pipeline wrappers (`vigil assess gau <endpoints|secrets|js-endpoints>`), signal-first work-buffer triage (`work-buffer reclassify`, `work-buffer clusters` — folded-in list-clusters, priority fetch/defer through `work-buffer`), scope helpers (`vigil assess scope <explain|filter>`), code-analysis flows (`code-sourcemap-extract` writes safe immutable `sourcesContent` trees/manifests and hands off explicitly to `code-ingest`; `code-ingest` owns publication; `vigil assess code-record <classify|modules|threat-model|analysis|variant-check|fuzz-decision|fuzz-campaign>` (the final three persist strict variant/fuzz completion receipts), filtered atomic `code-dispatch` queue claims/evidence-aware closeout, `code-coverage`, `code-size-summary`, `code-index build`, `code-index sync`), command-run audit search, audited host-side blue/non-Kali execution (`host-exec`, including `--require-audit` for blue WRITE actions), containment proposal approval (`approve-proposal`), exploit review/approval (`vigil assess exploit <review|approve>`), report readiness, and the **`kali_*` subcommands**. `kali_browser.py` owns the single Playwright/system-Chromium browser path: typed bounded steps, scope-routed attribution headers (the shared `lib/scope.py:host_admitted` matcher, mirrored into the container driver because request hosts are only known at run time), host-scoped identity material seeded from the initial URL plus every declared `navigate` step, identity-bound explicit storage state, and bounded evidence capture behind the existing `kali browser` verb. Scope data decides ATTRIBUTION only — it never aborts or filters a navigation (test-pinned). `--attribution-scope` is `scope` (default) or `all`; the only fail-closed case on the ATTRIBUTION axis is a program that mandates a header with no resolvable in-scope host, which refuses before navigation and names `--attribution-scope all` as the way past it. The verb's other refusal is the shared `--identity` one (`kali.py:prepare_browser_identity_material` / `_apply_identity_material`): an identity that is absent, `dead`/quarantined, or carries nothing injectable for the request host refuses rather than running anonymously and mislabelling `auth_context`; an advisory `stale` identity is still replayed, with a warning. `code-index build` writes backend-repo/generation/source-digest/structural-input-scoped artifacts, and `code-index sync` bridges their validated metadata to backend `code_files` rows.
- **Code source trust boundary.** `agent/scripts/assess/lib/code_snapshot.py` owns race-checked, content-addressed sealed source copies; its `code-source-manifest/v2` authenticates repository identity, Git provenance, the complete copied-file inventory, and complete `excluded_entries` accounting used at refresh commit. It also owns the one-safe-component `repo_key` validator; `code-ingest` normalizes unsafe name characters when deriving a key and validates explicit keys before any artifact path is built. `orchestrator/backend/app/code_snapshot.py` independently attests a requested verified snapshot at refresh commit: it opens the exact engagement-owned content-addressed path through no-follow descriptors, validates the v2 manifest and every real source byte/path/mode, reconciles staged metadata and declared counts, and keeps filesystem identities pinned through promotion. `verified` is therefore backend-derived rather than a caller assertion. `agent/scripts/assess/lib/trusted_exec.py` owns resolution and invocation of Git/ctags executables outside repository-controlled paths. `code-ingest` may read an origin checkout only while producing that sealed copy and Git provenance; every later source read uses the sealed `repo_path`. The backend retains the full sealed-snapshot digest as provenance while separately deriving `source_review_identity_digest` from the exact copied-file and exclusion inventories. Admitted-file, language, exclusion-boundary, or verified/unverified trust changes advance the active generation; a checkout path, branch, commit-label, or dirty-bit change with identical reviewed bytes and exclusions updates provenance without forcing every generation-bound review and index to restart. `agent/scripts/assess/lib/code_structural_identity.py` binds that sealed path/hash inventory to the current backend per-file language map and owns its canonical `structural-input-identity/v1` digest; the language layer normalizes only documented aliases such as `c++` to parser-canonical `cpp`. `code-index build` writes a generation/source/structural-input-bound `structural-index/v6` manifest under `tools/analysis-state/structural-index/`; files beyond the parser resource boundary receive an all-byte streaming security fallback with explicit unavailable/truncated dimensions rather than a silent skip. ctags writes under `tools/analysis-state/ctags/`; `code-index sync` validates the current schema and canonical languages before publishing through the backend's schema/generation/digest/hash compare-and-swap. The backend stores the accepted structural schema on `code_repos`; its additive migration deliberately defaults legacy rows to an empty schema, so an old generation/path pair cannot become current by appearance. Older snapshots and index artifacts remain retained history until an explicit pruning contract exists.
- **Legacy review-identity migration.** Why: an additive upgrade leaves `code_repos.source_review_identity_digest` blank. An exact verified refresh seeds that digest without advancing generation only when its full sealed-snapshot digest, source-manifest digest, and trust quality match the stored row. Any ambiguous difference advances conservatively because a legacy row cannot prove whether only Git/path provenance or the reviewed exclusion boundary changed.
- **Structural parser toolchain.** `agent/scripts/assess.py` owns the PEP 723 production dependency set for the assessment CLI; `orchestrator/backend/pyproject.toml` mirrors the same exact Tree-sitter runtime and grammar pins in its `dev` extra, and `orchestrator/backend/uv.lock` seals that test environment. Why: a `structural-index/v6` artifact is reproducible only when production parsing and contract tests execute the same parser/grammar versions.
- **Structural parser process boundary.** `agent/scripts/assess/lib/parser_boundary.py` owns the parent-side process, time, RSS, protocol, result, and cancellation limits; `parser_worker.py` owns the restricted child entrypoint. `code-index build` invokes exact parsers only through this boundary and converts every typed failure to a complete all-byte streaming fallback with explicit unavailable-dimension debt. `code-dispatch` separately owns bounded paginated selection, 10,000-match and 64 MiB pre-materialization caps, 200-row submission batches, and bounded outcome snapshots. The virtual million-file regression qualifies production listing/pagination, bounded exact-selector composition, one maximum-size 200-row commit, interruption, and idempotent retry; separate focused tests qualify multi-batch and outcome-cap behavior. It does not claim aggregate byte accounting or dependency closure because no such production consumer owns either contract.
- **CLI batch ergonomics.** Why: the entity id/slug positional is `nargs="+"` (one-or-more) on the finding-lifecycle verbs (`finding verify`, `finding update`, `finding link`), surface/coverage verbs (`resolve surface`, `resolve coverage-item` — the merged `resolve <target-kind> <id...>` verb, `resolve.py`), `approve-proposal`, and the `agent done` / `agent close` verbs (each runs a client-side per-id loop and reports a created/updated-vs-skipped/failed tally instead of failing the whole batch on one bad id). `finding update` and `finding verify` accept discrete flags, nested-object `--details-inline` / `--provenance-inline`, or a single-record `--payload-file`; the removed generic `--inline` form is a hidden error-only tombstone. Payload-file mode is exclusive with content flags. An update payload must name exactly one slug, include `expected_row_version`, and make `notes_mode` explicit when it carries `notes`, so an incrementally maintained finding JSON file remains the canonical non-lossy update path. The former `kill-finding` and `reset-finding` verbs folded into `finding verify --disposition false_positive` and `finding update --status draft` respectively (2026-07 CLI consolidation); `list-finding-group` folded into `finding list --root-cause <slug>`. `finding record` gained an `--allow-remint`/`--force` override paired with a new D4 re-mint guard: `orchestrator/backend/app/services/state_manager/findings.py` refuses to mint a net-new finding over an existing `false_positive` (killed) finding at the same `defect_family`/canonical location unless the override flag is passed. `finding list` gained a `--q` alias for `--search`.
- **Assessment engagement binding.** `agent/scripts/assess/lib/config.py` owns one fail-closed precedence rule for every `vigil assess` command: valid explicit `--engagement-dir`, else an engagement root discovered from CWD, else `VIGIL_SESSION_ENGAGEMENT_DIR` exported by `vigil engagement start`/bench launchers. An explicit bad path fails, a CWD/session disagreement fails, and a valid legacy `ENGAGEMENT_DIR` that disagrees emits a loud artifact-path warning without becoming a selector. `vigil use` and `ENGAGEMENT_DIR` remain global-service/runtime context only and never select assessment state. Kali sync/async execution derives its API key and working directory from that resolved directory and rejects either an injected directory mismatch or a configured key that differs from the directory basename. `lib/contracts.py` renders this invariant on every executable command contract so prompts do not duplicate it.
- **Submission export boundary.** `agent/scripts/assess/commands/export_submission.py` owns report-package generation and `export_reply.py` owns vendor-facing replies. Both ASSEMBLE and PRESENT; neither rewrites authored content, and there is deliberately NO automatic credential masking. Why: a blanket masking pass cannot distinguish the operator's own session cookie from a credential the target disclosed — which is often the finding's whole proof — collapsing every `curl -b` argument to one placeholder erases a multi-identity reproduction, and running over `details_json` as serialized text can consume a JSON escape, invalidate the document, and blank every details-sourced section while still exiting 0. Credentials, tokens, cookies, PII, and other captured evidence remain verbatim in the finding for editable renders and in the immutable byte record for sent-reply exports. The same rule governs the rest of both commands: `steps_to_reproduce` items render verbatim as list items (`lib/finding_render.py:step_lines` — no renderer-imposed `N.` counter and no stripping of an author's own numbering, so `2024. Renewal year …` ships as written), every prior reply body is inlined and fenced in draft/final-unsent reply renders, linked command runs pass through whole, and the authored `evidence_ref` is shown alongside the normalized one. **A link carrying `retired_at` is not evidence.** `_linked_command_runs` skips retired links before it fetches `command-runs/{id}`, so a superseded link costs nothing to drop and never reaches a triager as live proof; `export_reply.py` imports the same helper, so one filter covers both renders. `assessment_finding_links.retired_at` exists to PRESERVE a superseded link rather than delete it, which is why the filter lives on the export side: `finding link list` still shows retired rows, because that surface is the audit record and hiding them there would be the opposite bug. **The reproduction is transcribed, not inferred:** `details.repro_runs` (schema key 60) names the command runs that produced `steps_to_reproduce`, in step order, and `_repro_runs` fetches each row so OPERATOR DETAILS renders its REAL argv in a "Reproduction runs" block — separate from the linked-evidence runs because the two answer different questions ("what proves it" vs "what reproduces it") and a finding routinely has one without the other. Why: nothing else can tell a transcript from a plausible narrative, and only the specialist holding the live session can supply it — a report-writer cannot run probes, so an unrecorded reproduction is one it can only reconstruct from prose. **Nothing about repro runs GATES a publish.** Absent `repro_runs` and a declared id that does not resolve are both non-blocking `advisories` (a draft additionally marks an absent set with `[NEEDS: details.repro_runs]`, and unresolved ids are named in the render, on stderr, and in the context JSON as `repro_runs_unresolved`). Why not refuse on an unresolved id, when a fabricated one is exactly what this field catches: `_repro_runs` cannot tell a fabricated id from a run row that is momentarily unreachable, so refusing would let a backend hiccup block the publish of a finished, verified finding — the same reason title length is an advisory. Both lists stay in the author's declared order (parse and fetch run in ONE pass for that reason: splitting them would group malformed entries ahead of failed fetches and misalign the ids against their steps). `report_readiness` matches: empty `steps_to_reproduce` stays a `finding_field_quality` BLOCKER, unbacked steps are a `finding_repro_runs_missing` ADVISORY. Internal identifiers are FLAGGED non-destructively (`lib/finding_render.py` hygiene helpers) and any leak fails a final export closed; title length is a non-blocking `advisories` entry instead, since an editorial opinion must never gate a publish. `details_object` consumes the public API's parsed `details` object and reports a malformed object on stderr rather than degrading to `{}` silently, and `render_finding` prints `(unset)` rather than inventing `medium`/`unknown` for a field nobody set. Draft mode is diagnostic and renders missing markers; final mode fails closed unless the target finding is a reportable verified candidate, every outward-facing section (summary, reproduction steps, evidence narrative, impact, and remediation) is authored, its proof is a contained artifact linked to that finding, indexed, and present on disk at export time, target-specific readiness blockers and report hygiene warnings are clear, the output remains inside the engagement, and artifact registration succeeds. Weakness precedence is explicit template value, then `details.weakness`, then `details.cwe_id`. The JSON context distinguishes authored content proof from durable artifact proof.
- **Immutable submission-package boundary.** `orchestrator/backend/app/services/submission_versions.py` is the single service used by `vigil assess export submission` and the web UI. It revalidates the final workspace against the current finding/proof/readiness state, reads workspace and attachment bytes through no-follow descriptors, stages and fsyncs the package, verifies its digest, atomically publishes it, then records a completed append-only version and registers the package as an artifact. No attachments produces the exact Markdown bytes; selected registered/present/hash-valid artifacts produce a deterministic stored ZIP with `submission.md`, `attachment-manifest.json`, and `attachments/<artifact-id>-<basename>`. `assessment_submission_versions` in `app/db.py` owns per-finding numbering, source/hash/actor/time metadata, idempotent request identity, staging recovery, and completed-row immutability. `app/api/submissions.py` exposes bounded finding, completed-version, incomplete-version, failed-version, and cursor-based orphan-diagnostic pages plus export/download/recover to both consumers; the CLI consumes every diagnostic page and the web UI exposes explicit continuation controls. Recovery retains its validated caller surface in the append-only activity ledger before it attempts mutation. This boundary never changes `submission_status` and never submits externally; the finding remains the authored source of truth.
- **Immutable sent-reply boundary.** `orchestrator/backend/app/reply_render.py` is the single source of truth for the versioned exact UTF-8 outbound renderer (body plus authored new-evidence prose; never internal thread history); `agent/scripts/assess/lib/reply_render.py` is an import-only bridge so draft previews and the backend cannot fork the format. `record_reply.py --sent` runs the shared-renderer preview through the external-text hygiene gate, then calls `POST /assessment/submissions/{slug}/replies/{seq}/send` with only the expected finding row version and audit identity/reason. Inside one write transaction, `orchestrator/backend/app/services/sent_reply_versions.py` selects the persisted nonempty draft, invokes the canonical renderer, server-selects renderer identity/version, and binds the sent transition to `assessment_sent_reply_versions` in `app/db.py`; callers cannot supply bytes, digests, or renderer labels, and generic finding writes cannot create sent state. The row stores immutable bytes, positive sequence, byte length, SHA-256, renderer identity/version, and time. Every metadata/download read revalidates the bytes, while `export_reply.py` also verifies the downloaded length/digest before writing and never rerenders a sent sequence. The `[NEEDS: reply body]` marker is draft-only. ### Prompt-to-backend coupling

Prompt changes are NOT prompt-only when the prompts define artifacts that the backend stores or the CLI processes. Key coupling points:

- **`guidance_hypotheses`** — defined in architect prompts, stored in `code_analysis_queue.guidance_hypotheses_json` (db.py), normalized by `code_dispatch.py`, validated by `QueueItemRecord` / `RequeueItemRecord` (code_analysis.py API), and hydrated in service fetch/requeue logic. Keep it as `list[str]`: structured requeue trigger context now lives separately in `code_analysis_queue.cross_file_triggers_json`, so changes to either payload shape require backend + CLI updates together, plus prompt diff review.
- **`call-graph.json` / `attack-hypotheses.json` / optional `cve-bug-shapes.jsonl`** — filesystem artifacts written by Phase 1 and consumed by later code dispatches. The architecture-mapping skill owns the optional historical-shape artifact's evidence-backed one-object-per-line contract; Phase 2 consumes it only when present and keeps that discovery non-covering. Removing or weakening these artifacts breaks operator-core-code.md dispatch instructions and agent pre-work checklists.
- **`file-analysis-queue.json`** — filesystem artifact loaded into backend via the transactionally idempotent initial `code-dispatch queue` path. Schema must match `QueueItemRecord` fields or normalization fails: `priority` is a strict integer, is required, and must exactly equal the file's current band-valid `analysis_priority`, with whole-batch rejection before mutation on drift. Added depth is a separate `code-dispatch reanalyze <artifact> <reason>` contract with the same priority invariant: the service validates and links the new row to a completed predecessor (the nullable predecessor id is intentionally service-owned rather than a fresh-only SQLite self-FK, keeping migrations and cascade deletion consistent) and never treats an accidental duplicate insert as reanalysis. Trigger requeue is a distinct server-prioritized `queue_mode=trigger` writer: it rejects unclassified targets, transactionally merges trigger provenance into one unleased pending attempt, and cannot be overwritten by ordinary initial submission. Queue history remains append-only; one canonical latest-current-generation projection owns fetch, stats, file status, successful review/coverage, and trigger state. Fetch fails closed on overlapping active history; stats reports preserved older attempts as `historical_total` / `superseded_history`, inconsistent latest lease identity as `invalid_active_identity`, and overlapping superseded active work as `invalid_active_history`.
- **General rule:** if a prompt instructs an agent to produce structured output that an `vigil assess` command consumes, or that the backend stores/serves, the prompt and the consumer are coupled. Check both sides before changing either.
- **Reactive nuclei rule + Phase 1a/1b/1c structure** — `agent/operator-core.md` "Reactive Nuclei on URL Discovery" and the Phase 1 sub-phases (1a wildcard enum, 1b parallel recon+source, 1c reactive nuclei sweep) couple to `agent/skills/nuclei-scanning/SKILL.md` "Reactive Sweep Mode" for mechanics; the operator rule points at the skill rather than duplicating the `nuclei` invocation so both stay in sync. Phase 1/2 exit gates run `vigil assess check-phase-readiness --phase recon|collect`; dropping the gate call in `operator-core.md` silently disables the phase boundary check. Prompt and doc wording are reviewed through markdown diffs rather than repository tests; executable CLI/API contracts should be covered by their owning backend tests.

Aggregate/archive/retained-generation reads are no-follow regular-file reads, and the owner-controlled publication lock rejects symlinks and special files. Sync never migrates: it rejects legacy/wrong-schema aggregates and manifests before any backend publication. ### Anti-patterns flagged by review

These came up during the mid-engagement review and the consolidation work above. Read them before adding a new "small" invariant copy:

- **Hardcoded SQL `IN ('image', ...)`**: build the placeholders from `INERT_TYPES` (see `dispatch/work_items.py`'s `work-buffer reclassify` predicate for the pattern). Hand-typed inert sets in SQL are the most-frequent drift class in the codebase history.
- **"Almost-the-same" verb tuples**: don't fork `KALI_VERBS` into a target-facing-only copy by hand. Add to `KALI_TARGET_VERBS` or `KALI_MAINT_VERBS` and recompose.
- **Help-string verb lists**: build with `', '.join(_TUPLE)`. Hand-typed argparse help that lists actions ages out within a release.
- **"Looks like a schema, isn't a schema" (historical, retired ADR 0013)**: `agent/scripts/schema.sql` used to own only CREATE TABLE / CREATE INDEX for the local `cases.db`, with views and runtime migrations living in `db.py` so legacy DBs caught up on every `db_init`. The split-schema-vs-migrations lesson still applies to `orchestrator/backend/app/db.py` (the current, single schema owner) if a future change reintroduces a similar split there.
- **Operator reading skills**: skills are dispatched-to, not read by the operator (see `operator-core.md` step 5). The `--skills` flag exists for audit; the dispatch prompt carries the `path` for the specialist to load.
- **Editing generated wrappers**: never edit `agent/AGENTS.md`, `agent/CLAUDE.md`, or anything under `.claude/agents/` / `.codex/agents/` / `.opencode/agent/` / `.goose/recipes/`. They open with a `GENERATED FILE — DO NOT EDIT` banner; edit the source under `agent/operator-core.md` or `agent/agents/*.md` and run `agent/scripts/render-operator-prompts.sh repo`.

## Update Triggers

Update this file when a change does any of the following:
- adds, removes, renames, or moves a stable entrypoint;
- changes which file owns a contract or boundary;
- changes a generation or sync relationship;
- adds or removes a durable API/service/tab/CLI command family;
- changes which directory is the canonical home for a concern;
- touches a drift-prone depth-harness invariant (the canonical vuln taxonomy / app-framework token set / scorer weights+thresholds / `result_status` covering vocabulary / the §5.3 Expected-class predicate table) — these are data-driven and dated specifically so they age gracefully; adding a framework, class, or outcome value must be an ADDITIVE edit to the list, never a control-flow change, and the drift tests (`test_vuln_taxonomy.py`) must stay green so a newly-added skill/bucket that isn't wired fails CI instead of silently widening the blind spot;
- renames/moves a readiness gate — the function names `coverage_readiness` / `report_readiness` / `per_host_coverage` / `depth_ledger` and the HTTP routes `/coverage-readiness`, `/coverage-readiness/by-host`, `/report-readiness` are load-bearing (phase-transition gate, `report_export`, frontend) and must stay stable; add a new front door (like `phase_readiness`) that CALLS them instead.

Do not update this file for:
- implementation-only edits inside an unchanged boundary;
- temporary experiments, caches, or local machine state;
- field additions that do not create a new durable boundary.
