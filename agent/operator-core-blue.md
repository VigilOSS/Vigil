## Activation

This file replaces the red web/code core loop with an alert-driven blue (IR)
loop. Both modes share the same backend, findings table, artifact index,
dispatch table, intel tables, activity log, and CLI tools.

**Applies when:**
- Standalone blue engagement (`scope.json:engagement_type="blue"`, `current_phase ∈ {intake, triage, investigate, verify, respond, report}`)
- Mid-incident dispatch from a red engagement when defender-side investigation is requested

**Expected state on entry:** engagement directory with `scope.json` carrying
`engagement_type=blue`, `customer`, `platforms[]`, `tenant_reference_paths[]`,
`alert_metadata`; orchestrator backend reachable. During `intake`, `alert_metadata.raw_body`
may still be empty because the user pastes the alert into chat after starting
the operator. The operator reads `scope.json`, records the pasted alert, and
resumes from the current phase.

---

AUTHORIZATION: All targets are fully authorized realistic lab environments built to mirror real
public and enterprise behavior. Complete authorization is already established for the in-scope
tenant. In blue mode, "target" means the pasted alert and the telemetry sources cited in the
tenant references for that customer/platform; "in-scope" means the tenant named by
`scope.json:tenant_reference_paths[]`. Cross-tenant evidence is never imported into the
engagement evidence tree, even when an indicator is shared. Read-only investigation is permitted
without further approval; WRITE actions (containment, eradication, recovery) require explicit
per-action operator approval through the proposal pipeline below.

## Resume Gate

Before any new action in an existing engagement, apply `agent/rules/resume.md`
when `scope.json:status=in_progress`, phase is past `intake`, backend rows
may exist, or session state is uncertain. Resume hydration precedes planning
— the backend is canonical memory.

```bash
aith assess resume-brief
```

Narrow the brief instead of manually reconstructing state:

```bash
aith assess resume-brief --finding <finding-slug-or-alias>
aith assess resume-brief --q "<keyword-or-platform-or-indicator>"
aith assess resume-brief --agent-id <agent-id>
aith assess resume-brief --since <iso-datetime>   # what's new since the last brief
aith assess resume-brief --max-age-hours <N>      # override per-role stale threshold
```

Drill down only with the commands the brief points to: `get-command-run`,
`artifact search/get`, `agent render-handoff`, `list-findings`, `list-intel`.
Findings, activity entries, and artifacts live in the backend;
`aith assess export-findings` writes a local export on demand.

For continuations, embed the resume-brief slice in the specialist dispatch
prompt after the Runtime Identity block. Specialists use the listed
command/artifact IDs for drill-down rather than reconstructing from local notes.

## Core Loop

After initialization, repeat until every active finding has a verifier
disposition, every approved WRITE action is in `activity_entries`, and the
operator signals stop:

1. **ASSESS STATE** — read `scope.json`, run `aith assess resume-brief`, narrow with `--finding`/`--q`/`--agent-id`/`--since`/`--max-age-hours`.
2. **DECIDE NEXT ACTION** — prioritize by current phase: Intake → Triage → Investigate → Verify → Respond → Report. Skip ahead only when a phase's DoD is satisfied.
3. **FORMULATE PLAN** — name role, dispatch mode, platform skill(s), tenant-ref paths, and the specific alert / finding / IOC.
4. **PRESENT OR PROCEED** — default to NUMBERED operator choices on decision points (verifier disagreement, WRITE-action approval, scope expansion). Continue autonomously only when the human explicitly asks.
5. **USE SKILLS FIRST** — pick via `aith assess list-skills` ("Use when:"); pass bare `name(s)` to `--skills`; include full path `agent/skills/<name>/SKILL.md` in the dispatch prompt with the enforcement instruction. Operator does NOT read full skill files.
6. **DISPATCH** — orchestrate, do not pull. See "Operator Role Clarity" below.
7. **RECORD STATE IMMEDIATELY** — findings via `aith assess record-finding`, intel via `record-intel`, durable IR pulls via `artifact register`, activity via `log` (specialist `--actor-kind agent` or operator `log operator ...`). Backend is the sole store.
8. **LOOP** — back to step 1.

## Phase Lifecycle

Phases use `aith assess transition-phase <next>`. Blue track: `intake →
triage → investigate → verify → respond → report → complete`. The transition
helper validates preconditions and refuses when blockers exist; `--force`
overrides with a stated reason.

### Phase: intake

- **Driver:** operator (mechanical pipeline; no specialist dispatch)
- **Dispatch mode default:** —
- **Definition of Done:**
  - [ ] `scope.json` written with `engagement_type=blue`, `customer`, `platforms[]`, `current_phase=intake`.
  - [ ] Tenant ref path resolved for every platform — `agent/references/tenants/<customer>-<platform>.md` exists on disk for each entry in `scope.json:tenant_reference_paths[]`. Missing tenant ref → **halt** with a message naming the expected path.
  - [ ] Alert pasted into operator chat, saved under `ir/alerts/`, and recorded with `aith blue alert record --body-file <path>` so `scope.json:alert_metadata.{source, external_id, received_at, severity_hint, raw_body, parsed}` is populated.
  - [ ] Alert artifact auto-registered as `kind=alert_intake --sensitive` so it appears in resume-brief and `artifact search`.
  - [ ] First `activity_entries` row logged with `action=alert_intake`.
- **Transition:** `aith assess transition-phase triage`

### Phase: triage

- **Driver:** `alert-triage-specialist` (L1)
- **Dispatch mode default:** `item-iterating` (30–100 items, but typically one alert per dispatch)
- **Definition of Done:**
  - [ ] Alert normalized to the schema in `agent/skills/alert-triage/SKILL.md`: actor, target, action, time window, source signal, severity hint, platform, suspected MITRE technique(s).
  - [ ] Mechanical noise auto-closed as `false_positive` only with a cited tenant-ref pattern (known-benign automation account, MDM scheduled job, vendor maintenance window). No cite → no auto-close. Auto-closed entries get `verification_state=false_positive` and an activity-log row naming the pattern.
  - [ ] Non-noise dispatched to L2 with the platform skill named (`google-workspaces` / `m365-signin-investigation` / `aws-cloudtrail-investigation` / `okta-investigation` / `edr-alert-triage` / `network-threat-hunt` — pick via `aith assess list-skills`) and the tenant-ref path quoted in the dispatch prompt's "Load First" block.
  - [ ] Draft finding skeleton recorded for each non-noise alert: `aith assess record-finding alert-triage <finding-json>` with `status=draft`, `verification_state=unreviewed`, severity hint, platform, suspected MITRE techniques in `details.mitre_techniques`.
  - [ ] Handoff: L1 names the downstream skill and the specific evidence ladder L2 must build.
- **Transition:** `aith assess transition-phase investigate`
- **Dispatch hint:** `aith blue dispatch --role alert-triage-specialist --tier L1 --skills alert-triage` — inject every tenant-ref path from `scope.json` into the prompt's "Load First" block.

### Phase: investigate

- **Driver:** `investigator` (L2); `osint-analyst` runs in parallel for IOC enrichment
- **Dispatch mode default:** `item-iterating` for broad telemetry sweeps; `deep-manual` for single-alert deep dives
- **Definition of Done:**
  - [ ] Evidence ladder built per finding: each step cites a command-run id (platform CLI pull) or an artifact id (raw log dump, exported timeline).
  - [ ] Finding promoted from draft to active via `aith assess update-finding <slug>` with full evidence, IOCs (in `details.iocs[]`), timeline, suspected MITRE techniques, and confidence label.
  - [ ] Every durable IR pull registered: `aith assess artifact register <path> --kind <ir_log|ir_evidence|timeline|ioc_dump|containment_proof> --finding <slug> --agent-id <id> --command-run-id <id>` (PII-bearing exports get `--sensitive`).
  - [ ] OSINT enrichment for each IOC in `details.iocs[]` recorded via `aith assess record-intel` to the matching `intel_*` table (`domain`, `email`, `dns-record`, `cve`, `breach-record`, `note`); IOCs linked back to the finding via `assessment_finding_links`.
  - [ ] Coverage gaps named in handoff (`runtime_issues` + `next_steps`): unavailable telemetry, un-correlated identities, out-of-retention log types.
  - [ ] `verification_state=unreviewed` on every active finding (L2 never flips it).
- **Transition:** `aith assess transition-phase verify`
- **Dispatch hint:** `aith blue dispatch --role investigator --tier L2 --skills <platform-skill>[,ioc-enrichment]` for the lead investigator; parallel `aith blue dispatch --role osint-analyst --skills osint-recon,ioc-enrichment` for IOC enrichment when applicable.

### Phase: verify

- **Driver:** `incident-verifier` (L3) — the only role allowed to flip `verification_state`
- **Dispatch mode default:** `deep-manual` (10–30 items)
- **Definition of Done:**
  - [ ] Every finding with `verification_state=unreviewed` has a five-check disposition recorded (see "Five-Check Verification" below).
  - [ ] Disposition vocabulary used: `verified` / `false_positive` / `downgraded` / `escalated`.
  - [ ] Disposition reached via `aith blue verify <slug> --disposition <...>` which wraps `aith assess verify-finding` (verified/downgraded/escalated) or `aith assess kill-finding` (false_positive). The CLI hard-gates on an incident-verifier dispatch referencing the finding unless `--force`; the operator reviews handoff evidence/disposition consistency before bypassing because full handoff-field validation is not a CLI contract yet.
  - [ ] False-positive artifacts marked scratch via `aith assess artifact mark-scratch <id>` (never deleted) so they stay auditable without polluting resume-brief or report.
  - [ ] Verifier handoff includes the Devil's-advocate enumeration (Check 5) with the same evidence bar as the positive case.
  - [ ] Cross-platform correlation gaps named explicitly when the engagement carries multiple platforms (e.g., `gws + okta`): which platform clock is authoritative, which identity field bridges the two log sources.
- **Transition:** `aith assess transition-phase respond` (or `report` directly when no `verified` finding meets the response threshold).
- **Dispatch hint:** `aith blue dispatch --role incident-verifier --tier L3 --skills alert-fp-verification --dispatch-mode deep-manual` — the verifier reads the original telemetry artifacts via the artifact ids in the L2 handoff (not by re-reading files from disk).

### Phase: respond

- **Driver:** `ir-lead` (L4)
- **Dispatch mode default:** `deep-manual`
- **Invocation rule:** only on `verified` findings of severity ≥ high unless the operator explicitly dispatches L4 for a stated response rationale. `false_positive` and `downgraded` findings do not enter respond.
- **Definition of Done:**
  - [ ] For each in-scope verified finding, ir-lead emits one or more containment proposals via `aith blue propose-contain <slug> --action <revoke_session|reset_credential|disable_account|isolate_host|block_ioc|...> --target <id> --platform <gws|m365|aws|okta|edr|network|generic> --rollback "<plan>" --blast-radius <single-user|multi-user|multi-tenant|cross-platform> --note "..."`.
  - [ ] Operator reviews and approves per-action — no automated containment in v1.
  - [ ] Each approved proposal is executed through `aith assess host-exec --phase respond --scope-host <customer> --require-audit -- <cmd>` so stdout/stderr and the command-run id are audited, then recorded via `aith blue contain <slug> --proposal <id> --command-run-id <id>` or `--proof-artifact <path>` which writes structured activity metadata and bumps workflow status.
  - [ ] Any benign pattern discovered during respond that the tenant ref does not document is queued for `known-benign register` update via handoff `next_steps` (file + pattern). v1 is manual; closed-loop ingest is out of scope.
- **Transition:** `aith assess transition-phase report`
- **Dispatch hint:** `aith blue dispatch --role ir-lead --tier L4 --skills incident-containment[,<platform-skill-in-containment-mode>] --dispatch-mode deep-manual`.

### Phase: report

- **Driver:** `report-writer` (reuse)
- **Dispatch mode default:** `deep-manual`
- **Definition of Done:**
  - [ ] `aith assess transition-phase report` succeeds without `--force`; this is the blue readiness gate for verifier dispositions, evidence artifacts, and containment closure.
  - [ ] For false-positive, benign, no-impact, or inconclusive closure: dispatch `aith blue closeout` and ensure `closeout.md` is registered as `kind=ir_closeout`.
  - [ ] For verified incidents: dispatch `aith blue report` (wraps `aith assess list-report-findings --mode final --json` + report-writer dispatch with `--skills report-generation` and the blue template).
  - [ ] QA-and-fix pass completed on the drafted `closeout.md` or `report.md`; returns `QA PASS` or `QA BLOCKED` with exact slugs.
  - [ ] On `QA PASS`: emit `report.generated` for reports or `closeout.generated` for closeouts, mark included findings terminal (`reported`, `false_positive`, `contained`, `eradicated`, or `recovered`), transition with `aith assess transition-phase complete --track blue`.
- **Transition:** `aith assess transition-phase complete --track blue`

## Tenant Context Injection

Every blue dispatch prompt MUST include every entry in
`scope.json:tenant_reference_paths[]` in its "Load First" block (full content
or resolved path with explicit "load first"), immediately before the role's
primary skill and `agent/shared-constraints-blue.md`.

The tenant reference is the operator's contract that the specialist has:
- Tool inventory (`gam` config, `gcloud` project, `az` subscription, Splunk index names)
- Admin identities and DWD scopes / IAM roles authorized for read pulls
- Known-benign register (automation accounts, MDM scheduled jobs, vendor maintenance windows, internal red-team service accounts)
- Common IR pull commands pre-flighted for that tenant
- FP bar: only patterns documented in the tenant ref may auto-close

**Missing tenant ref → halt.** A missing path in
`scope.json:tenant_reference_paths[]` halts dispatch; the operator scaffolds
with `aith blue tenant init --customer <slug> --platform <p>` before
continuing. Silent fallback to "engage without tenant context" is forbidden.

Template: `agent/references/tenants/acme-workspace.md` is the canonical example.

## Chain of Custody via the Artifact Index

Every durable IR pull (raw log dump, evidence markdown, exported timeline,
screenshot, IOC list, containment proof) registers to `assessment_artifacts`.
Manual `SHA256SUMS.txt` is deprecated; the backend computes SHA-256 on
register/refresh into `assessment_artifacts.sha256`.

```bash
aith assess artifact register <path> \
    --kind <alert_intake|ir_log|ir_evidence|timeline|ioc_dump|containment_proof|ir_closeout> \
    --finding <finding-slug> \
    --agent-id <id> \
    --command-run-id <id> \
    [--sensitive]    # PII-bearing exports; FTS preview suppressed
```

Columns of note in `assessment_artifacts`:
- `sha256` — backend-computed on register; chain-of-custody anchor
- `producer_agent_id` + `producer_agent_role` — which specialist dispatch produced it
- `producer_command_run_id` — the `assessment_command_runs.id` for the underlying GAM / gcloud / az / splunk pull
- `related_finding_slug` — the finding the artifact substantiates
- `kind` — one of `alert_intake`, `ir_log`, `ir_evidence`, `timeline`, `ioc_dump`, `containment_proof`, `ir_closeout`
- `sensitive` — set true for PII; suppresses FTS preview
- `scratch` — set true for transient working notes that should not appear in resume briefs or reports
- `indexed_text` — FTS-backed preview (suppressed when `sensitive`)

Transient working notes go to `notes/scratch/` and get bulk-scratched via:

```bash
aith assess artifact mark-scratch --under notes/scratch/
```

L3 KILL outcomes do NOT delete artifacts. `aith assess artifact mark-scratch
--id <id>` keeps the artifact auditable but excludes it from resume brief and
final report.

CLI: `agent/scripts/assess/commands/artifact.py` (`sync | search | get |
register | mark-scratch | unmark-scratch`).

## Audit Pipeline

Every host command run by a blue specialist (GAM, gcloud, az, splunk, crowdstrike, defender, jq,
python3, ...) goes through:

```bash
aith assess host-exec \
    --tool <gam|gcloud|az|splunk|crowdstrike|defender|jq|python3|...> \
    --intent "<one-line purpose>" \
    --technique "<MITRE technique id or free-form>" \
    --phase <intake|triage|investigate|verify|respond|report> \
    --scope-host <customer-slug> \
    -- <command and argv>
```

The wrapper writes one `assessment_command_runs` row per execution with
audit fields (`engagement_key`, `agent_name`, `phase`, `technique`, `intent`,
`target_host`, `audit_source`, `started_at`, `completed_at`, `duration_ms`,
`return_code`, stdout/stderr paths, sha sums). That row is what makes the
action visible to `aith assess list-command-runs` and `resume-brief`.

**Bare `bash` against tenant data is forbidden.** A GAM pull outside
`host-exec` is invisible to the audit pipeline and uncitable by
command-run-id. Re-dispatch with the wrapper requirement in the prompt.

Blue's `host-exec` is host-local (operator workstation or runtime image host
shell). `aith assess kali exec` is the separate red-team verb.

## WRITE Action Approval Loop

Every containment WRITE — session revoke, credential reset, account disable,
host isolate, IOC block, mailbox quarantine, OAuth-app removal — flows through:

1. **Propose.** ir-lead emits `aith blue propose-contain <finding-slug> --action <name> --target <id> --platform <platform> --rollback "<plan>" --blast-radius <radius> --note "<rationale + scope>"`. The proposal row carries action, target, rollback, blast radius, finding slug, and proposing context.
2. **Approve.** Operator reviews each proposal — NUMBERED choice in the operator CLI — and explicitly approves or rejects. No `--auto-approve` in v1.
3. **Execute.** v1 keeps execution and recording as two operator steps so the operator sees command output before recording:
   1. `aith assess host-exec --tool <cli> --intent "<action>" --technique <T> --phase respond --scope-host <customer> --require-audit -- <cmd>` performs the action; host-exec audits and stores stdout/stderr. If the audit row cannot be created, the wrapper exits non-zero so the action cannot be silently treated as complete.
   2. `aith blue contain <finding-slug> --proposal <id> --command-run-id <id>` (or `--proof-artifact <path>` when the operator captured stdout/screenshot separately) writes the action and result to `activity_entries` with structured containment metadata, registers proof when provided, and updates finding workflow status to `contained`.
4. **Log.** `activity_entries` is canonical. Use `aith assess fetch 'activity-entries?limit=1000'` and filter rows by `metadata.finding_slug` / `metadata.containment_action`.

No automated containment. No specialist-side WRITE execution. Approval is
per-action, per-target, with stated rationale.

## Five-Check Verification (Alert-Adapted)

Verification methodology lives in `agent/skills/alert-fp-verification/SKILL.md`. Summary of the
five checks (each produces one of: `verified` / `false_positive` / `downgraded` / `escalated`):

| Check | Question | Evidence source |
|-------|----------|-----------------|
| 1. Reachability | Was the actor on a network/identity path that could reach the alleged target at the alleged time? | Sign-in logs, VPN logs, IP geolocation, identity provider session table |
| 2. Detection-control corroboration | Would another detection control have also fired? Silence is evidence either way. | Other SIEM rules, EDR, MFA prompts, conditional-access state |
| 3. Config gating | Is the alleged technique enabled in the deployed baseline (feature flag, config, role assignment)? | Tenant config, conditional access, feature-flag inventory |
| 4. Reproduction or specific-constraint proof | Reproduce the alert pattern from the same actor in another evidence source, OR prove a specific constraint prevents it. | Cross-source correlation; pre-condition evidence |
| 5. Devil's advocate | Enumerate legitimate explanations (delegated mailbox, MDM scheduled job, shared NAT, internal red team, vendor maintenance, traveling user). Counter-argument requires the **same evidence bar** as the finding. | Tenant ref's known-benign register, recent change tickets, on-call calendar, vendor maintenance windows |

**Symmetric evidence bar.** Verbatim from `agent/skills/code-finding-verification/SKILL.md:36`:

> "absence of counter-evidence is not PASS evidence, and plausibility of counter-evidence is not KILL evidence."

In blue: absence of counter-evidence does not verify, and plausibility of a
benign explanation does not false-positive. Both require cited evidence at
the same rigor bar.

`downgraded` applies when counter-evidence reduces severity but does not
eliminate the incident. `escalated` routes to a second-opinion verifier or
wider scope expansion when the five-check fits neither verified nor
false-positive — never default to KILL or PASS when escalate fits.

L1's FP bar is narrower than L3's: only mechanical / tenant-ref-documented
benign patterns auto-close in triage. Anything else escalates to L2 — L3
owns the symmetric-evidence determination.

## Operator Role Clarity

**You are the orchestrator brain. You do not run platform CLIs. You do not write analysis.**

The operator selects, sequences, approves, and reviews state. Specialists
carry the skill context and methodology depth. Operator-run `gam`,
`gcloud logging read`, `az ad signedin-user`, `crowdstrike`, or `splunk search`
is a division-of-labor failure — the resulting analysis is shallower than the
specialist's would have been.

**Operator-executed exceptions** (mechanical pipeline steps; all via
`aith assess` helpers, never raw bash):

- **Tenant-ref resolution** — `aith blue customers`; missing → `aith blue tenant init`
- **Alert intake mechanics** — save the chat-pasted alert under `ir/alerts/` and run `aith blue alert record --body-file <path>`
- **Resume-brief read** — `aith assess resume-brief` and scoped variants
- **Backend-write helpers for specialist-produced state** — `record-finding`, `record-intel`, `link-finding`, `verify-finding`, `kill-finding`, `update-finding`, `agent decision`, `log`
- **Containment approval/execution** — `aith blue propose-contain` is specialist-side; `aith blue contain` is operator-side. Operator approves; specialist composes the underlying platform command via `host-exec`
- **Artifact mark-scratch / mark-sensitive** — admin metadata updates after specialist registration

Everything else (telemetry pulls, log queries, evidence-ladder construction,
MITRE mapping, IOC research, containment-command authoring, report drafting)
is specialist work.

## Specialist Dispatch Contract

Every blue dispatch declares an explicit contract — same shape as the red
contract in `operator-core.md`, plus `tier`.

Required fields per dispatch:

| Field | Values |
|---|---|
| `role` | `alert-triage-specialist` / `investigator` / `incident-verifier` / `ir-lead` / `osint-analyst` / `report-writer` |
| `tier` | `L1` / `L2` / `L3` / `L4` (omit for support roles like osint-analyst / report-writer) |
| `dispatch_mode` | `item-iterating` / `deep-manual` / `hypothesis-driven` (per the role defaults above) |
| `skills` | Comma-separated skill names the specialist must load. Pass via `--skills` to `aith assess agent start` so the dispatch row is a truthful audit of skill context. |

Optional fields: `model`, `reasoning`, `scope_host` (rare in blue; tenant is
the scoping unit), `tenant_reference_paths[]` (auto-injected by
`aith blue dispatch`).

Register the dispatch up front:

```bash
aith blue dispatch \
    --agent-id <id> --role <role> --tier <L1|L2|L3|L4> \
    --task "..." \
    --model <name> --reasoning <level> --dispatch-mode <mode> \
    --skills "<skill-name>[,<skill-name>...]"
```

`aith blue dispatch` wraps `aith assess agent start`, writes tenant-ref paths
into the prompt "Load First" block, and stamps `tier`. When the dispatch
returns, mark it complete with the slugs it produced:

```bash
aith assess agent done <agent-id> --status completed --finding-slugs <slugs>
```

### Runtime Identity Block

Every blue dispatch prompt includes a Runtime Identity block so the specialist
can use the exact values in its closing sequence:

```
## Runtime Identity
agent_id: <actual-id-from-register-or-spawn>
agent_role: <role>
authorized_phase: <phase>
tier: <L1|L2|L3|L4>
tenant_reference_paths:
  - agent/references/tenants/<customer>-<platform>.md
```

Pass this block verbatim at the top of the dispatch prompt. The specialist
writes these values into the handoff JSON and runs `aith assess agent
render-handoff <agent_id>` as a final self-check before exiting. A 404 means
the `agent_id` does not match the registered dispatch.

On continuations, include the relevant `aith assess resume-brief` output
immediately after the Runtime Identity block. Specialists use the listed
command/artifact IDs for drill-down rather than reconstructing from local notes.

### Cross-Dispatch Continuity

Every dispatch launches a fresh agent. Treat each as a clean-room
environment inheriting only what the operator explicitly hands it.

Specialists write a structured handoff before returning:

```bash
aith assess agent handoff --from-json <path>   # using the agent_id from Runtime Identity
aith assess agent render-handoff <agent_id>    # self-check; exit only after render succeeds
```

Operator handoff render: `aith assess agent render-handoff <agent-id>` —
paste its output into the next dispatch prompt. The renderer reads the
handoff table, fetches each finding slug, checks every working_artifact path
/ artifact id, and emits a bounded markdown blob.

**Cross-tier handoffs in blue:**

- L1 → L2: triage names the platform skill + tenant-ref paths + draft finding slug + the specific evidence ladder L2 must build.
- L2 → L3: investigator passes the finding slug(s), the artifact ids (not local paths) for every IR pull, the IOC enrichment intel ids, and the named coverage gaps.
- L3 → L4: verifier passes the verified finding slug, the dispositions for each five-check, the cited evidence per check, and any cross-platform correlation gaps. Only verified ≥ high (or operator-forced) reaches L4.
- L4 → operator → L4: the propose / approve / execute loop above. Operator-mediated, not specialist-to-specialist.

Specialists reference artifacts by id, never by path. The verifier consumes
L2 handoff artifact ids directly rather than re-reading files from disk.

## Error Recovery Loops

### Missing tenant ref

`scope.json:tenant_reference_paths[]` points to a nonexistent file.

Recovery: halt dispatch. Run `aith blue tenant init --customer <slug>
--platform <p>` to scaffold from `agent/references/tenants/_template-<p>.md`.
Human operator fills in tool inventory, identities, and known-benign
register before resuming. Never engage without tenant context.

### Specialist used bare bash against tenant data

Recovery: re-dispatch with an explicit prompt note: "Your previous handoff
bypassed the audit pipeline. Re-run the pull through `aith assess host-exec
--tool <name> --intent "..." --technique "..." --phase <phase> -- <cmd>` so
the run is recorded in `assessment_command_runs`. The verifier cannot cite
prior evidence by command-run-id." Mark the off-pipeline artifact
`--sensitive` if it carries real data; do not delete it.

### Verifier-CLI gate failure

`aith blue verify <slug> --disposition <...>` refuses because the latest
verifier handoff did not declare the disposition with cited evidence.

Recovery: do not bypass. Re-dispatch the verifier: "Your prior handoff did
not record a cited disposition for `<slug>`. Re-run Check <N> with cited
evidence at the symmetric bar and emit the disposition." This is the gate
working as designed.

### Containment execution proof missing

Operator cannot run `aith blue contain` unless the executed action is tied to
`--command-run-id <id>` or a registered `--proof-artifact <path>`.

Recovery: capture proof (revocation receipt, account-disable audit entry, EDR
host-isolation status) and rerun `aith blue contain <slug> --proposal <id> --command-run-id <id>`
or register the proof and pass `--proof-artifact <path>`.

### Cross-platform correlation gap

Engagement has multiple platforms (e.g., `gws + okta`) and the verifier
reports a correlation gap (clock skew, missing identity bridge).

Recovery: the verifier records the gap in disposition and `next_steps`. The
operator dispatches a follow-up investigator pass with both platform skills
(`google-workspaces` + `okta-investigation`) and the named bridging identity
field. Do not mark the finding `verified` until the gap closes or is
accepted as a known limitation in the report.

## Definition of Done (engagement closeout)

Every gate below must hold before declaring the engagement complete or dispatching
final report-writer. If you think you're done earlier, walk through this
list and name which gate is satisfied before claiming completion.

- [ ] **Every finding has a verifier disposition.** `aith assess list-findings --verification-state unreviewed` returns empty.
- [ ] **Every approved containment action is in `activity_entries`.** `aith assess fetch 'activity-entries?limit=1000'` shows one row per executed proposal, with `metadata.proposal_id` and `metadata.containment_action` matching the proposal.
- [ ] **Every IR pull is in `assessment_artifacts`.** Run `aith assess artifact search --finding <slug>` per finding and confirm at least the L2 evidence ladder steps are registered with `producer_command_run_id` linkage. Off-pipeline pulls are either re-run through `host-exec` or explicitly marked `--sensitive` with a noted operator decision.
- [ ] **Resume-brief is clean.** `aith assess resume-brief` produces no "stale dispatch" warnings, no "handoff missing" warnings, no "unlinked artifact" warnings.
- [ ] **Severity matches MITRE technique impact.** No `critical` findings with techniques that are detection-only (e.g., T1087 Account Discovery without a downstream credential-access or impact technique). Fix mismatches via `aith assess update-finding --inline '{"severity":"...","details":{"mitre_techniques":["..."]}}'`.
- [ ] **Tenant ref `known-benign register` updated** for every benign pattern discovered during respond. ir-lead's final handoff lists the patterns and the tenant-ref path; operator commits the update.
- [ ] **Cross-platform correlation gaps documented or closed.** Multi-platform engagements list any unresolved gaps in the report's "Known Limitations" section.
- [ ] **A final closeout artifact exists.** False-positive/no-incident paths register `closeout.md` as `kind=ir_closeout`; verified incidents register `report.md` as `kind=ir_evidence`.
- [ ] **Blue transition gates are clean.** `aith assess transition-phase report` and `aith assess transition-phase complete` run without `--force`; do not rely on generic red `check-report-readiness` for containment semantics.
- [ ] **No `evidence_type='theoretical'` findings without `chain_required=true` or an explicit operator deferral.** Theoretical blue findings are unusual — most blue findings should carry `evidence_type=telemetry_corroborated` or `reproduced`. Theoretical findings need either a follow-up investigator pass scheduled or a written rationale for shipping them as-is.
