# Phase 1 — Reconnaissance

**Read-on-phase-entry.** When you ENTER Phase 1, Read this doc; re-read it on a method re-anchor (Core Loop "Re-anchor on method mid-run" in `AGENTS.md`). It carries the full Phase-1 sub-steps (1a operator-owned enum job, 1b recon + source, 1c reactive nuclei), the exit gate, and the `check-phase-readiness` calls. Cross-phase machinery (Core Loop, Subagent Dispatch contract, Recon Dispatch Resource Policy) stays in `AGENTS.md` and `agent/references/runtime-guides/dispatch-resource-policy.md`.

1. **Phase 1 — Reconnaissance**

   **The operator owns the long recon enumeration; specialists do the bounded, judgment work.** 1a subdomain/host enumeration runs as the operator-owned supervised job `vigil assess recon` (the operator launches it and polls `vigil assess recon-status`) — never a specialist's blocking call, because a >~5-min blocking enum gets the dispatched agent SIGUSR1-killed mid-run (`agent/shared-constraints.md` §2). Only 1b (per-host web fingerprint assessment) and 1c (reactive nuclei) are dispatched to `recon-specialist` and `source-analyzer`. The operator handles scope prep, resource thresholds, the recon-job lifecycle, and durable-state recording. Operator carve-outs are the mechanical pipeline checks in Core Loop step 7's "Operator-executed exceptions" (`AGENTS.md`) — credential auto-use validation, tier-pick smoke, runtime health smoke, backend-write helpers, and bulk mechanical probing. Everything else target-facing is specialist work. If a specialist cannot be launched (missing skill, missing wrapper, runtime down), record the blocker via `vigil assess agent decision --kind dispatch_blocked --phase 1b --reason "..." --surfaced-to-user` (the row carries `kind=dispatch_blocked` plus `surfaced_to_user=true`) and surface to the user — never silently move analysis work back into the operator loop.

   **1a. Subdomain/host enumeration — the operator-owned recon job (when the engagement declares `*.domain` roots)** — launch `vigil assess recon <apexes> --background` (stages dns-discovery → web-discovery → js-mining → gau; checkpointed/resumable) and poll `vigil assess recon-status` to completion BEFORE the 1b recon+source pass, because 1b's per-host assessment and 1c's reactive nuclei both consume the live-host set the job produces — running them against the apex alone misses the enumerated surface. Run it as the supervised job (not a specialist dispatch) so the long enumeration survives a harness timeout; the pipeline ingests resolved live hosts into the work buffer itself and merges confirmed, admitted wildcard children into the engagement's derived host inventory. Add `--brute` / `--resume` for a deeper pass when the recon-status digest shows the surface is incomplete.
   Before launching the `vigil assess recon` job, run `vigil assess kali exec --technique HEALTH --intent "verify subdomain-enum runtime binaries" --probe-kind fingerprint --phase recon --timeout 30 -- which alterx asnmap bbot cero dnsx github-subdomains massdns puredns shuffledns subfinder tlsx` to confirm tooling. Missing binaries → fix the runtime, do not silently degrade — puredns silently fails when massdns is missing (zero output, no error, exit code 0), and a dnsx fallback against a typical bruteforce wordlist will spike container CPU before stabilizing. Recon-specialist dispatches scanning multiple hosts MUST use `nmap -iL hosts.txt`. The operator never asks a specialist to loop nmap per-host; always consolidate with `-iL`. If the specialist generates `for h in hosts; do vigil assess kali nmap-scan --target $h ...`, the operator catches it in dispatch review and re-dispatches with the consolidated command.
   Skip 1a when the engagement declares only bare hosts — there is nothing to expand, so launching the recon job adds no surface.
   - **Register out-of-scope carve-outs in `scope.json` `out_of_scope` BEFORE enum runs.** Wildcard expansion routinely surfaces hosts the program excluded (telecom-PTR space, a vendor apex, an explicitly carved-out subdomain). The `vigil assess recon` pipeline scope-filters the resolved set between the dns and web stages (the same `host_admitted` allow-AND-not-deny primitive `scope filter` uses), so authoring the deny-list up front keeps the bulk httpx/katana passes — and downstream buffer — off out-of-scope hosts from the first probe. Carve-outs added after a run only take effect on the next `--resume`. To sanity-check a specific host's verdict before or after editing the carve-outs, run `vigil assess scope explain <url-or-host>` — a read-only oracle over the same primitive that reports admitted/denied, the exact allow/deny entry that drove it, the program's attribution headers and rate ceiling, and a vendor-SaaS warning (no writes, no network).
   - **Vendor-SaaS scope checkpoint.** When the first Phase 1 recon dispatch returns wafw00f / nmap rDNS / httpx fingerprint output that flags a host's underlying application as vendor-managed SaaS (strict-subdomain match on CNAME or rDNS), warn once per host and record the flag via `vigil assess agent decision --kind scope_decision --host <host> --vendor <vendor> --choice pending --surfaced-to-user`. The detection requires recon output, so the checkpoint fires AFTER the first recon dispatch returns, not before — surfacing it pre-dispatch is circular (vendor-SaaS detection needs the dispatch's output). The default policy is permissive: warn and continue. The checkpoint blocks Phase 1 advance only when the operator opts in via `vigil assess check-phase-readiness --phase recon --strict-vendor-saas`. The flagged options for the user are: (1) in-scope per VDP — proceed with recon; (2) out-of-scope per VDP — skip and exclude from buffer; (3) partial scope — test the asset's surface but not the underlying vendor platform. Hosts `vigil assess scope explain` identifies as explicit literal roots skip the gate entirely — the literal is already the operator's in-scope decision.
   - **Egress reputation checkpoint.** Run `vigil assess egress-check --hosts <in-scope hosts> --control example.com --emit-blocked-hosts <file>` after the recon job's dns/web stages populate the live-host set. The verb retries ambiguous TLS failures, captures bounded header/body evidence, and records every outcome as an advisory `egress_decision`. A failed control, an unclassified sample, or a WAF/edge-block response is **inconclusive**: one control cannot prove estate-wide, per-host, or per-route reachability. Only a control-live, overwhelmingly transport-blackholed sample produces `cluster_blackholed` and the blocked-hosts file for `ingest endpoints --egress-blocked-hosts`. Re-sample that verdict after five minutes before surfacing the four mitigation options in `agent/references/runtime-guides/cdn-ip-blocking.md`: allowlisting, an explicitly authorized clean egress, a browser path when the evidence is TLS/browser-fingerprint-shaped, or accept and document the coverage gap. Record the operator's choice with its evidence-backed percentage; never infer the cause from a bare 403/000 percentage.

   **1b. Recon + source analysis** — dispatch `recon-specialist` + `source-analyzer`. On a **dedicated** runtime run them in parallel (their work is independent and sequential dispatch doubles wall time for no coverage gain). On a **shared / Standard-tier** runtime, default to the sequential monitored pipeline instead (see `agent/references/runtime-guides/dispatch-resource-policy.md` → "Phase-1 dispatch shape"): N concurrent heavy-enum agents on a shared VM is what caused the load-36 near-crash. `recon-specialist` reads the completed `vigil assess recon-status` digest (it does not generate the host list — the 1a job did), judges recon completeness, and runs the bounded per-host web fingerprint chain via `agent/skills/web-recon/SKILL.md` (continuing non-web triage when a meaningful service is exposed). `source-analyzer` loads `agent/skills/source-analysis/SKILL.md` and focuses on HTML/JS/CSS extraction. If recon finds a non-web service that needs deeper follow-up and a relevant skill/reference exists, dispatch the most suitable worker before leaving Phase 1 — leaving non-web triage on the operator loses the skill's methodology depth.

   **1c. Reactive nuclei sweep against Phase 1 URL delta** — before leaving Phase 1, fire a reactive nuclei sweep via `vigil assess kali nuclei` against the URL delta from the recon job (1a) and the recon-specialist assessment (1b) (methodology + dedup in `agent/skills/nuclei-scanning/SKILL.md` "Reactive Sweep Mode"). Running it in-phase — instead of holding every URL until Phase 4 — turns template hits into `intel record` / `finding record` writes *before* Phase 4 specialists dispatch, so specialists inherit the signal as intel and findings. The dedup pattern (`command-run list` + jq) ensures this pass and the Phase-2 reactive pass (in `agent/phases/phase-2-collect.md`) do not re-scan the same host+template combo.

   **Phase 1 exit gate.** Before leaving Phase 1, run `vigil assess check-phase-readiness --phase recon`. The gate checks whether each scope entry has downstream evidence — live services, recorded surfaces, or work-buffer rows under the entry's host. Also audit that every expected pipeline stage COMPLETED (none `timed_out` / `partial` / never-ran) — `check-phase-readiness` surfaces this as a stage-completion audit; the how lives in `agent/skills/phase-qc/SKILL.md`. Bare hosts and URL entries pass trivially; wildcards fail when enumeration produced nothing real. If a wildcard fails, re-run or extend the recon job (`vigil assess recon … --brute --resume`) or mark the entry deferred in `scope.json` before advancing, because entering Phase 2 with empty scope branches leaves whole subtrees of the attack surface untested.

   **Per-host outcome audit (WARN-only).** Pair the scope-entry gate with `vigil assess check-phase-readiness --phase recon --by-host` to surface a per-host outcome table: WAF tier, service inventory, directory-fuzz coverage, tech fingerprint, OSINT. The audit reads outcome tables (`intel_tech_components`, `assessment_services`, `assessment_surfaces`, `assessment_dispatch_decisions`) — never `assessment_command_runs` — so any tool that wrote the durable row satisfies the corresponding objective. Unmet objectives WARN with an actionable dispatch hint but do not block phase advance. When an objective is intentionally skipped (scope brief forbids brute-force, vendor confirms WAF tier out-of-band, OSINT carve-out), record an explicit deferral: `vigil assess agent decision --kind coverage_deferral --payload-json '{"host": "api.example.com", "deferred_objectives": ["directory_fuzz"], "reason": "scope brief forbids brute-force"}' --surfaced-to-user`. The deferral row is queryable post-engagement via `vigil assess agent list --kind coverage_deferral`, so gaming the gate is audited rather than invisible.
