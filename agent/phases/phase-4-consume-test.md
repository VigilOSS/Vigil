# Phase 4 — Consume & Test

**Read-on-phase-entry.** When you ENTER Phase 4, Read this doc; re-read it on a method re-anchor — this is the depth-bearing phase and the one whose cadence drifts toward breadth/item-ticking on long runs, so re-reading the Depth Doctrine here is the countervailing cue. It carries the Depth Doctrine / Per-Domain VA Fan-Out, the Phased mindset flow (which pass sets each lane's mindset), the nuclei coverage audit (step a), the per-type consumption loop (steps b–h), and the system-level cross-surface synthesis (step i). Cross-phase machinery (Iteration-mode Declaration, Specialist Dispatch Contract, Recon Dispatch Resource Policy → Aggregate concurrency) stays in `AGENTS.md` and `agent/references/runtime-guides/dispatch-resource-policy.md`.

For the commands below, set:

```bash
DIR="${ENGAGEMENT_DIR:?set by the engagement launcher}"
```

4. **CONSUME & TEST** → operator-orchestrated. Load `agent/skills/case-dispatching/SKILL.md`.

   **Depth framing — a surface can be a whole application.** A single surface or URL is frequently an entire application that warrants its own deep campaign, not a one-probe item: katana crawl, content discovery, a parameter sweep, an IDOR sweep across its object references, JS/secret extraction, and a dedicated specialist dispatch (or several) scoped to that one app. The most common way real bugs are missed on large runs is treating a high-value surface as a quick tick instead of going deep on it. When a surface looks like an app — an authenticated portal, an API root, an admin console — dispatch a campaign against it, not a single check.

   ### Depth Doctrine — Per-Domain VA Fan-Out

   **Breadth-bias is the dominant failure mode at scale.** The operator's pull toward breadth — covering everything, resolving each surface to a status, advancing the phase — silently degrades the hunt: it favors quicker checks, which means fewer vuln-class checks per surface, which means shallow depth, premature closure, and missed vulnerabilities. The countervailing doctrine for Phase 4 is depth, expressed as a *concentrated* fan-out, not a swarm. This is the operator-side complement of the Re-anchor cue (Core Loop in `agent/operator-core.md`) and Core-Loop step 2's Phase-4 prioritization — re-read both when the cadence drifts back toward item-ticking.

   - **Focus 1-2 TARGETS at a time; a SURFACE can BE a target.** At any moment, concentrate the active fan-out on one or two targets — where a "target" may be a single high-value surface (an auth portal, an API root, an admin console), not necessarily a whole apex. Set `--scope-host` to the focused domain for every dispatch in the batch. When a hot lead emerges, converge concurrent disjoint-host lanes on it; once the lead is resolved, **re-widen back to breadth** — converge and release, not permanent narrowing.
   - **Fan VA lanes at DEPTH, not a swarm.** Partition the focused target's surfaces into lanes keyed on **(surface-group × vuln-class × mindset)** — e.g. lane A = the API surface group × access-control/IDOR × `idor-bac.md`, lane B = upload/form surfaces × injection + file-upload × `injection-surface.md`, lane C = auth/session surfaces × auth-logic × `business-logic.md` — one `vulnerability-analyst` per lane, each loading the matching vuln-class skill AND the matching mindset from `agent/rules/mindsets/` (see "Phased mindset flow" below for which pass sets the mindset), running a real campaign at `item-iterating`/`hypothesis-driven` depth. This is **deep** fan-out: it is the opposite of the corpus `swarm` mode (which is many shallow `low`/`medium` scans over a corpus — see Iteration-mode (dispatch_mode) Declaration). Do not use `swarm` here.
   - **Phased mindset flow gates which mindset each lane loads.** The mindset axis of the lane key is set mechanically by a coverage-driven wide→deep→exploit schedule, never chosen from a flat menu — a lane's `mindset lens` field (Specialist Dispatch Contract) is a function of which pass the lane is in and which family the wide pass's signal pointed at, not an operator free-choice:
     - **Pass-1 WIDE** — `hunt_scope: wide`, `dispatch_mode: hypothesis-driven` (broad sampling — NOT the deep `item-iterating` cap; see the `hunt_scope` ↔ iteration-mode pairing under Iteration-mode Declaration), open objective, baseline mindset (`agent/rules/adversarial-mindset.md`) plus `agent/rules/mindsets/developer.md` only, no family lens yet. Sweeps the focused target's surfaces broadly and records per-family **signal** (which vuln-class each surface leans toward) rather than confirming or killing anything.
     - **Pass-2 DEEP** — `hunt_scope: deep`, one family mindset (`idor-bac.md`, `injection-surface.md`, `business-logic.md`, or the closest fit) plus the matching vuln-class skill, dispatched per signal/high-yield cell the wide pass flagged — this is the lane fan-out the bullet above describes.
     - **Pass-3 EXPLOIT** — `exploit-developer` loaded with `agent/rules/mindsets/chain-impact.md` for cross-lane chain synthesis over the confirmed set (see the exploit-developer fan-out bullet below).
     - **Which roles carry the lens in each pass.** The Dispatch-Mindset slot is not VA/EX-only — every vuln-hunting role has its own `## Dispatch Mindset` slot and the flow sets which pass fills it. In the WIDE survey pass, `source-analyzer` carries the survey lens (baseline + `agent/rules/mindsets/developer.md`) as it maps code/surface for per-family signal, exactly as a wide VA does. In the DEEP pass, the family lens is injected on the roles that drill a flagged cell: `vulnerability-analyst`, `fuzzer` (payload-family lens — typically `injection-surface.md`), `code-vuln-hunter`, and `code-variant-hunter` (the sibling/variant lens of the confirmed family) each load the matching `agent/rules/mindsets/` packet into their own slot, the same way VA does. In the EXPLOIT pass, `exploit-developer` carries `chain-impact.md`. Recon / surface-collector / osint / report-writer / blue roles do NOT carry a family mindset — they precede or follow the lens-driven hunt rather than hunting a vuln-class under a lens.
   - **Exploit-developer fan-out for high-value targets (low-bias, chain-synthesizing).** On a rich, high-value target where slow+thorough beats breadth, fan **`exploit-developer`** (deep-manual) across the same surface lanes — but give each lane the **full surface + intel context with a deliberately OPEN objective** ("find and prove P1/P2 impact on this surface"), NOT a pre-named bug. This is **Pass-3 EXPLOIT** in the phased mindset flow above — load `agent/rules/mindsets/chain-impact.md` on every dispatch in this fan-out; it is the generative lens for which chain to pursue and when to stop, not a replacement for the exploit-developer's own A→B Chain Table. Pre-pointing biases the hunt and hides chains; the exploit-developer self-serves the full endpoint map and is told to "start with the landscape, then narrow." The operator's job is **cross-dispatch chain synthesis**: after each batch, read the lanes' handoffs together, look for A→B primitives across them (auth-bypass + IDOR, reset-poisoning + takeover, info-leak + SSRF), and only THEN dispatch chain-directed follow-ups. Run several under-directed lanes first; let the chain context accumulate across dispatches before you start steering. This complements (does not replace) the VA fan-out — use VA for breadth-of-vuln-class discovery, exploit-developer fan-out when the target warrants concentrated deep manual hunting.
   - **Scale lane count to surface count — within the runtime-tier ceiling.** Thin surface = 1 VA lane; a broad, app-like target = 3-4 lanes. The Heavy/Comfortable concurrency floor (4-6 specialists; see "Aggregate concurrency + shared-VM ceiling" in `agent/references/runtime-guides/dispatch-resource-policy.md`) is the budget on a dedicated runtime. **But the runtime tier caps the lane count regardless of surface breadth:** the Standard tier handles ~2-3 concurrent lanes on a small target (see "Resource sizing" in `AGENTS.md` / "Aggregate concurrency" in `agent/references/runtime-guides/dispatch-resource-policy.md`); do not fan 5-7 lanes into a VM that cannot absorb them. Size the fan-out to the smaller of (surface breadth, VM capacity).
   - **The "very little attack surface" exception.** Breadth-style coverage of many surfaces at once is acceptable in exactly one case: the target genuinely has very little attack surface — operationally, a handful of routes, no object references, no privileged features, no auth boundary, and no useful source intel *after a thorough pass* (not after a quick look). This is the only exception to 1-2-target focus; rotate to breadth only when the focused target is genuinely dry, per `agent/rules/hunting.md` (rules 5 and 15, "rotate only when genuinely dry").
   - **Closed-surface dead-vs-unfinished re-audit.** Before any phase exit, re-audit every surface previously resolved `covered`/`deferred`/`not_applicable` and separate genuinely **DEAD** surfaces (truly exhausted — varied probes across multiple vuln classes produced nothing) from **UNFINISHED** ones (resolved on a timer, a single quick pass, or one status-code check). Re-open the unfinished ones and fan a lane at them. The Phase-4 exit step `h` (`check-phase-readiness --phase consume`) resolves surfaces to a status but does not, by itself, distinguish dead from prematurely-closed — that judgment is this re-audit.
   - **Cross-lane politeness = disjoint hosts.** Assign lanes **disjoint hosts** wherever possible, and cap target-facing concurrency at **≤1 active target-facing tool per host across all lanes** (the I-013 disjoint-host concurrency rule: concurrent in-container probes against the same host thrash the resolver and risk false negatives). Tie this to the per-target rate calibration (`agent/references/runtime-guides/dispatch-resource-policy.md`) and the named-identity `--identity` disjointness (Credential Auto-Use → Named identities). This is a politeness/safety CUE, not a CLI-enforced gate.
   - **Bookend the fan-out.** Each focused target's fan-out is bracketed by the two Mandatory Phase-Exit Passes: the per-finding variant/sibling pass (Verify → Exploit) per confirmed finding, and the cross-target chain-construction pass (Exploit → Report), which runs **across** targets after each target's fan-out completes. See "Mandatory Phase-Exit Passes".

   ### Lens Vocabulary — Finer-Grained Failure-Family Lenses

   **Dispatch one mindset lens per specialist; cycle across batches.** Name exactly ONE mindset lens per Pass-2/Pass-3 dispatch — a family of related developer assumptions that fail together — never a menu the specialist chooses from. A lens is not a bug: it describes *how the developer was thinking*, so the specialist derives its own hypotheses instead of executing a pre-named checklist; naming the bug caps depth at the operator's guess, naming the lens lets the specialist generalize to every surface the family touches. Beyond the current `agent/rules/mindsets/` library files, these finer-grained failure-family lenses remain valid to name explicitly when the signal is more specific than a family file — most map onto `developer.md`'s cognitive-state patterns or `business-logic.md`'s state-machine lens:

   | Lens | What fails together |
   |---|---|
   | Caching | stale invalidation, shared-key leakage, cache-key injection |
   | Data handling / over-trust | caller-supplied values accepted without re-validation, over-broad deserialization |
   | Race conditions | TOCTOU, non-atomic credit/inventory, session-merge |
   | Mass assignment | unfiltered bind, hidden field promotion |
   | Upload / file handling | extension bypass, path traversal on store, content-type trust |
   | Client-side trust | server echoes client-controlled values, DOM sink injection |

   **Lens rotation:** a winning lens on a worked surface → re-run it on NEW surfaces (the same failure mode recurs wherever the same developer pattern exists); a fresh lens on an already-worked surface → dispatch it now (a surface proven clean under caching assumptions may still be vulnerable under race or upload assumptions). Cycle mindsets/lenses across batches — the operator names the surface and the mindset/lens, the specialist originates every hypothesis under it.

   ### Mid-Phase Cadence

   **Run the readiness check every few batches, not just at the end.** Run `check-phase-readiness` (the consolidated readiness command) every few dispatch batches during the phase — it is an advisory, EV-ranked view of what is under-covered and where the depth is thin, and it steers the next batch toward the gaps. Treating it as an end-of-phase gate only surfaces the gaps after the cheap moment to fill them has passed.

   **Read the coverage ledger to spot uncovered real-app hosts.** `vigil assess coverage` is the read-only, per-host coverage **LEDGER** — a reporting projection, NOT a gate. For each in-scope host it shows the live `route_count`, whether it is a `real_app?` (≥ `--route-threshold` distinct LIVE routes OR an exposed API/auth/GraphQL surface, OR-included even under the threshold), whether it has a `recorded-verdict?`, and the computed **coverage-state**. A host counts as **covered** ONLY with a *recorded verdict* — a finding, or an evidence-backed-negative such as a `false_positive` decision — NOT a merely completed dispatch. The ledger surfaces the gaps the later `check-phase-readiness` gate will block on: `uncovered` real-app hosts that still need a lane, and hosts flagged `needs_browser_reprobe` (curl undercounts routes behind a WAF, so re-probe with a browser before treating the host as thin/dead). Use it as the at-a-glance "which in-scope host has no verdict yet" view between batches; pass `--json` for the structured ledger.

   ### Steps

   a. **Nuclei coverage audit** (once, before the work-buffer loop) — audit what Phase 1/2 reactive sweeps already covered and run nuclei only against gaps. Do not blindly re-sweep: if every in-scope live host already received the reactive template set, this step prints a coverage summary and advances.
      1. Build the coverage set: `vigil assess command-run list --q nuclei --tool-bin nuclei` → jq-extract each prior run's input-list path and template tag(s).
      2. Compute gaps: live targets ∖ covered hosts (and/or template sets the reactive passes did not exercise).
      3. If gaps exist, run nuclei via `vigil assess kali nuclei` against the gap list only:
         `vigil assess kali nuclei -l /engagements/$ENGAGEMENT_KEY/scans/nuclei_gap.txt -t http/cves/,http/misconfiguration/,http/exposures/,http/default-logins/ -severity medium,high,critical -as -stream -jsonl -rate-limit 150 -c 25 -bs 25 -o /engagements/$ENGAGEMENT_KEY/scans/nuclei_gap_$RID.jsonl --technique CVE-VALIDATION --intent "Phase 4a gap-only nuclei coverage audit" --probe-kind fingerprint --phase consume-test --timeout 1800`
      4. If no gaps, record `vigil assess log operator "Phase 4a coverage audit" "check-phase-readiness --phase consume" "Reactive sweeps covered all in-scope hosts, no rerun needed." --actor-kind operator`.
      See `agent/skills/nuclei-scanning/SKILL.md` "Coverage Audit Mode" for the detailed procedure. Triage policy is unchanged: critical/high hits → work-buffer priority entries or findings (after manual validation); medium → intelligence.

      **Substrate-sweep scoping.** A broad nuclei substrate sweep is not politely completable at host-scale (templates × hosts blows up — a curated tag selection can still resolve to >1,500 templates × every live host). Scope it:
      - **Severity + cheap subset.** Default to high+critical plus the curated cheap directory subset above (medium hits route to intel, not findings). Scope by template **DIRECTORIES** (`-t http/cves/,http/exposures/,http/default-logins/,http/exposed-panels/`), not broad `-tags`. The wrapper now default-excludes the destructive/noisy classes (`dos`/`fuzz`/`intrusive`/`brute-force`) — you do not pass `-etags` for those yourself.
      - **Host-scale guard.** At ~25-50+ live hosts, do NOT sweep all in-scope live hosts. Bound the substrate sweep to a small dedicated/origin (non-CDN) subset — identify it from the recon origin-IP axis (asnmap → cero on resolved origin IPs) and the Cloud-fronted-vs-Origin trait rows in `agent/references/recon/rate-calibration.md`. On high-friction/large-host-count surfaces, prefer OSINT version→CVE matching (`osint-analyst` → `intel record cve` + targeted `exploit-developer` validation, see Phase 6) over a broad CVE-template host-scale sweep — it delivers most of nuclei's CVE-detection value without the per-host request volume.
      - **OOB-up-before-blind-testing.** Confirm shared OOB/interactsh is ready (`vigil oob status --json`) before any nuclei templates that fire blind/OOB payloads.
      - **gf-tags-are-leads.** gf buckets only classify; their hits are leads requiring downstream validation, never findings on their own.
      - **Operator-sweep-vs-VA-lane collision rule.** Either run the substrate sweep to **completion before** any VA lane touches those hosts, OR fold the scoped per-host-subset nuclei call into the VA lane that owns that subset. Do not run an operator-wide nuclei sweep concurrently against hosts a VA lane is actively probing (it violates the ≤1-target-facing-tool-per-host politeness rule and double-loads the host). The nuclei-scanning skill holds the mechanics; this is the scoping decision.
   b. Reset stale work items: `vigil assess work-buffer reset-stale 10`
   c. Check stats: `vigil assess work-buffer stats`
   d. Fetch and route — dispatch mode depends on pending-item volume:
      - **Pending < 2000 → type-based dispatch.** Independent types run in parallel:
        - `api`, `api-spec`, `form`, `upload`, `graphql`, `websocket`, `auth_entry`, `workflow`, `api_route`, `event_feed`, `debug_config`, `portal_session` → vulnerability-analyst (pick matching vuln-class skill via `vigil assess list-skills`)
        - `page`, `javascript`, `stylesheet`, `data` → source-analyzer (load `source-analysis` skill)
        `vigil assess work-buffer fetch <type> 10 <agent-name>`
      - **Pending ≥ 2000 → priority-first dispatch.** Type-based fetch orders only by id within a type, so at 2000+ pending items specialists churn through low-signal work before reaching the high-signal clusters `work-buffer reclassify` already scored. Switch to priority mode. `fetch-by-priority` is route-aware: it only ever claims rows whose type maps to a specialist route, and rejects free-form agent names so stray labels can't silently mix work types.
        - `vigil assess work-buffer fetch-by-priority 10 auto` — claim the highest-signal routable rows globally and stamp each with its canonical owner (`vulnerability-analyst` for API/auth/workflow/debug/portal/event types, `source-analyzer` for page/javascript/stylesheet/data). Use this when dispatching both specialists in parallel off one queue.
        - `vigil assess work-buffer fetch-by-priority 10 vulnerability-analyst` (or `source-analyzer`, or any `vulnerability-analyst-N` / `source-analyzer-N` instance label) — claim only the types that specialist can handle. Use this when you want parallel instances of one role without handing any of them work outside its route.
        Rows come back sorted by `priority_score DESC, cluster_key, id`. Run `vigil assess work-buffer clusters` between batches to decide whether new clusters warrant `defer-cluster` before they reach specialists — cluster keys carry a prefix (`gf:` for vuln-class buckets like `gf:ssrf` / `gf:debug_logic`, `path:` for the two-segment fallback); see `agent/skills/case-dispatching/SKILL.md` for the full weight table.
      Pass the raw fetched JSON rows into the dispatch context. They carry canonical ids such as `request_variant_id`, `service_id`, and sometimes `coverage_item_id`, which subagents need for durable probe and coverage writes.
      For blind testing, tell specialists to use `vigil oob status --json` to confirm shared infrastructure, start a named listener with `vigil oob client start <name> --engagement <key> --agent <agent>`, mint a nonce-tagged correlation URL with `vigil oob mint`, and correlate hits with `vigil oob poll --client <name>` (NOT `vigil oob client logs`, which is a raw listener tail for infra debugging only).
      If `$DIR/.listener_url` exists, include the tunnel address for agents that need a callback target.
   e. On subagent return: `vigil assess work-buffer done "id1,id2,..."`
      Mark a batch done only after the subagent has written durable state for any findings, significant probe runs, and coverage updates its work satisfied. Verify that EVERY pending coverage_item the surface accrued moved out of `pending`/`queued`/`deferred` — one per implied vuln-class, NOT just the cluster winner's. A single surface carries one coverage_item per matched gf bucket (a surface clustered `gf:ssrf` whose params also imply `sqli` accrues both an `ssrf` and a `sqli` item); closing it after testing only the cluster class is the breadth-bias failure mode that leaves the true class untested. `check-phase-readiness --phase consume`/`verify` surfaces the residual as the depth ledger's `signal_classes_uncovered` — the specific high-signal classes a surface's gf coverage_items implied that still lack a CLASS-SPECIFIC probe (a family being "covered" by a sibling class does NOT satisfy a distinct class in it). Drain those before closing — the resume-brief's `## Per-Input Coverage` grid shows exactly which input was probed for which class as which identity, so you can tell a genuinely untested cell from one already covered before dispatching another probe. On a decisive-surface or high-confidence `deep_required` unit, an unresolved BLOCK_HIGH class here is not merely advisory — it is the exact gap that holds the unit at the terminal report/complete edge (`agent/rules/hunting.md` "A URL can be a whole application"; escape via deep-testing or a recorded `depth_deferral`), so drain it now rather than carrying it to report time. If the agent skipped durable recording, send it back to write the state instead of silently duplicating it from the operator. Record surfaces via `vigil assess record-surface`. Re-ingest new endpoints via `vigil assess ingest endpoints`.
   f. If vulnerability-analyst signals FUZZER_NEEDED for a parameter or directory, dispatch fuzzer with `agent/skills/parameter-fuzzing/SKILL.md` or `agent/skills/directory-fuzzing/SKILL.md` and a bounded objective (target URL, parameter name, max payloads).
   g. Repeat b-f until pending=0 for all consumable types.
   h. Before leaving: `vigil assess check-phase-readiness --phase consume`. If it fails, resolve each remaining surface as `covered`, `deferred`, or `not_applicable`. High-risk surfaces (`account_recovery`, `dynamic_render`, `object_reference`, `privileged_write`) must be resolved as `covered` or `not_applicable` before leaving this phase — deferring high-risk surfaces means they become invisible to the report.
      `check-phase-readiness --phase consume` relays the surface-level coverage gate AND the broader scope-entry-level consumption gate (a whole scope host is fully consumed or explicitly deferred, not just individual surfaces), plus the depth ledger and intel advisory.
   i. **System-level synthesis (cross-surface).** Per-type consumption is surface-local. Some findings exist only *between* surfaces: an auth boundary one host enforces and a sibling host does not, or a capability chain across findings (info-disclosure + open-redirect, SSRF + token leak, IDOR + impersonation). Build seams the same way as code Phase 2D — **structural** (findings/surfaces sharing an auth context, host, or trust boundary) and **capability** (pair findings by primitive, bucketed by capability so it stays O(capabilities²) not O(findings²)) — and scale the dispatch to the seam count: one `vulnerability-analyst` in `hypothesis-driven` mode for small scope, or a `vigil assess agent start-swarm` fan-out (one worker per 1-3 seams) for large multi-host scope, then a reduce pass for multi-hop chains. Tokens are not the constraint; coverage is (`agent/rules/hunting.md §16`).
