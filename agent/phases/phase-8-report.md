# Phase 8 — Report

**Read-on-phase-entry.** When you ENTER Phase 8, Read this doc; re-read it on a method re-anchor. **Per the Core Loop re-anchor scoping, do NOT read this doc during Phases 1–6** — the Report walkthrough and the Definition of Done below are report-time judgment, and re-reading them mid-run is exactly the reporting-prematurity bleed that scoping prevents. Read it only once `vigil assess check-phase-readiness` shows the pre-report phases (through Exploit) clear. It carries the draft → targeted-evidence → checklist/QA → blind-triage → publish gate for the **default per-finding submission closeout** (android runs this same core and this same report flow — there is no separate android core), the optional internal-report mode, and the **Definition of Done** (the judgment-only closeout that no command can check). Cross-phase machinery stays in `AGENTS.md`.

8. **REPORT** → keep reporting inside the existing `report` phase. **Per-finding submissions are the default closeout** — use a draft → targeted-evidence → checklist/QA → blind-triage → publish gate per finding so each submission is reviewed before lifecycle state changes. The internal `report.md` (step f) is optional and operator-requested; it does not gate or substitute for the per-finding closeout below.
   **Before scaffolding anything — settle how many tickets this set is.** Decide the ticket count
   ONCE, across the whole reportable set, before any finding is drafted: re-drafting after a
   dup-close wastes the submission, and splitting a root cause across two tickets under-states its
   blast radius to the program. For every pair of findings in the set, answer one question: **would
   the same programmatic fix resolve both?** If yes, they are one root cause and file as ONE
   submission with the second folded in as a sibling — `vigil assess finding link <sibling> --root-cause
   <root-slug> --effect eliminates_finding`. If each needs its own distinct fix, they stay separate
   tickets — `--effect eliminates_attack_path` when they share an attack path but not a fix. A read
   and a write on one broken endpoint is usually one fix and one ticket; two endpoints missing the
   same check are usually still one fix if the check lives in shared code, and two tickets if it
   does not. Reach the answer from where the fix would land in the code, not from how similar the
   two findings look. Review the resulting clusters with `vigil assess finding list --root-cause
   <root-slug>`; `check-phase-readiness --phase report` surfaces the clusters it can see, but the
   same-fix judgement is yours and it is not inferable from the finding rows.

   **Repro rehearsal — before `report-writer` dispatch.** Dispatch a fresh
   `vulnerability-analyst` for live findings, `code-vuln-verifier` for source-only
   findings, or `code-fuzz-engineer` for fuzz/crash findings. Give it only the
   finding's `details.steps_to_reproduce` and `details.repro_runs`, with no author
   handoff or chain narrative. A successful check means the tester follows the
   authored steps and observes the claimed outcome: a command's zero exit code
   alone is insufficient. Live and fuzz checks cite all authored `repro_runs`
   IDs checked plus at least one completed cold-verifier command-run ID;
   source-only checks name the independently observed source result. Stamp the
   result with the tester's real dispatch ID using `vigil assess agent decision
   --kind repro_rehearsal`; `vigil assess contract agent decision` owns the payload
   fields and verdict rules.

   `followed` clears the finding for step a. `failed` routes it back to the specialist that recorded
   it — with the exact step and the exact breakage — not to the report-writer, which cannot run
   probes and can only paper over the gap with plausible prose. Rehearse before drafting, not after:
   a repro fixed at draft time has already cost a submission round, and a blind triager judging an
   unfollowable reproduction is a wasted pass.

   **A cut re-opens it.** `report-writer` may drop steps while authoring, bounded by the
   fabrication rule at `agent/agents/report-writer.md` Mandatory Closing Sequence step 1 — a
   dropped precondition is exactly the defect class this gate exists to catch, so a drop sends
   the finding back through this same rehearsal before publish, reusing the `repro_rehearsal`
   decision kind and contract above. Final export compares the decision's
   server-stamped digest with the current steps and ordered run IDs. For a wording-only
   change, a fresh independent tester may record `verdict=equivalent` with
   `prior_decision_id` of a successful `followed` check and a concrete `reason`;
   that declares equivalent steps without claiming a new run.

   a. **Scaffold (per finding, default):** for each reportable finding, dispatch `report-writer` in submission mode: `vigil assess export submission <finding-slug> --platform <bugcrowd|hackerone|direct> --draft`. This renders `$ENGAGEMENT_DIR/submissions/<slug>/submission.md` + `submission-context.json` FROM the finding's own fields (the finding is the source of truth) and consolidates the finding metadata, any hygiene warnings, the structured proof, and every linked command run into ONE "OPERATOR DETAILS — NOT FOR SUBMISSION" reference section below the second `---` in the local workspace. The external body and final delivered package exclude that section. Report-writer authors the body sections FROM what the command produces, it does not hand-assemble the draft. `--draft` never sets `submission_status`; it does not emit any event or mark the finding `reported`.
   b. **Author + write back to the finding (same dispatch):** report-writer authors the stable sections (Summary, Steps to Reproduce, Evidence, optional Attack Scenario, Impact, Remediation), resolving every `[NEEDS: ...]` marker with real backend-sourced content (title, severity + CVSS vector, platform taxonomy, attacker-impact statement, concrete proof), and writes each section BACK to the finding via `--payload-file` (the default write path — see "Submission-First Closeout" step 3 in `agent/skills/report-generation/SKILL.md`) so it holds exactly what would be sent, with `steps_to_reproduce` as one authored, self-numbered string the renderer reproduces verbatim. **Steps to Reproduce is bounded by a fabrication rule, not frozen:** every command, argv, and response value must trace to a `details.repro_runs` id (the "Reproduction runs" argv in OPERATOR DETAILS) — within that boundary report-writer may renumber, reword, merge, label, add expected-result lines, and drop steps, which re-triggers repro rehearsal above. It still cannot run probes, so outside that boundary it may reconstruct nothing from handoffs, chain narratives, or the finding's prose — see `agent/agents/report-writer.md` Mandatory Closing Sequence step 1 for the authoritative rule. An empty or unbindable `steps_to_reproduce` is `QA BLOCKED` back to the operator, and the finding goes back to the specialist that held the session. **Evidence is authored, not tool-dumped:** report-writer builds it from the OPERATOR DETAILS section's structured proof and linked command runs PLUS a targeted `vigil assess command-run list --q "<the finding's specific url/param/header/uri>"` (`--show-matches` / `--match-all` as needed) to catch reproducing runs the linked set missed, links any it finds (`vigil assess finding link <slug> --link-kind evidence --target-kind command_run --target-id <run_id>` — durable reference), then preserves exact values, annotates the proof lines, and stores that authored Evidence in `details.evidence`. Authored prose and inline PoC remain supporting material; satisfy the durable-proof requirement shown by `vigil assess contract export submission`. Verify a verb before citing it through `vigil assess list-commands --grep <term>` or its contract.
   c. **Checklist/QA (Pass 1 — in-context):** report-writer re-renders from the finding (`vigil assess export submission <slug> --platform <same> --draft --overwrite`) and runs the one consolidated pre-submission / report QA checklist in `agent/references/submission-format.md` against the re-rendered `submission.md` — the same checklist SKILL.md's "Post-Generation Self-Review" points to (verbatim evidence, internal identifiers, mandatory fields, banned phrasing per `agent/rules/reporting.md` Rule 20), fixes what it can at the SOURCE (the finding, then re-render — a fix made only in `submission.md` is lost on the next render), and returns `QA PASS` or `QA BLOCKED` with the exact gap and required operator action. This is the first of the two-pass gate: full context, fixes the finding; it does not reliably catch whether impact was actually demonstrated.
   If finding GET shows `verification_audit.claim_review_pending`, dispatch a fresh
   verifier to compare the edited claim with the verified one. Record its
   `claim_equivalence` verdict using the current transition ID and digest shown
   by finding GET; `vigil assess contract agent decision` owns the payload. An
   equivalent edit clears the pending review, while a changed claim returns for
   terminal verification. Report readiness and final export block until settled.
   d. **Blind pre-submission triage (Pass 2):** every **Medium-or-above** submission gets a fresh general-agent review before publish, using `agent/skills/blind-triage/SKILL.md`. After QA passes, re-render the complete `--draft` workspace and run `vigil assess export triage-packet <slug> [--attachment-id <id> ...]` with exactly the attachments intended for delivery. Give the reviewer only the packet's external `submission.md`, attachments, program brief, and rubric. Record its verdict with the packet's `packet_id`: `vigil assess agent decision --kind blind_triage_verdict --payload-json '{"finding_slug":"<slug>","packet_id":"<64-char packet id>","reviewer_dispatch_agent_id":"<reviewer-id>","writer_dispatch_agent_id":"<writer-id>","verdict":"<Accept@P1..P5|Need-More-Info|Not-Applicable-Informational|Out-of-Scope|Duplicate>"}'`. A non-Accept result goes to the writer for repair and a new blind pass. Final export re-renders under strict rules and checks the latest Accept against its external body, attachment bytes, platform, brief, and rubric; any content difference needs a new packet and review.
   e. **Publish (per finding):** only after `QA PASS` (Pass 1) AND, for Medium-or-above findings, a recorded `Accept` blind verdict (Pass 2), re-run `vigil assess export submission <finding-slug> --platform <same platform> --overwrite` **without** `--draft`. Final mode enforces the executable gate documented by `vigil assess contract export submission`; resolve any non-zero diagnostic at the finding instead of bypassing it. It never sets `submission_status`. Then mark the finding lifecycle: `vigil assess finding update <slug> --status reported --reason "Submission cleared for delivery" --source-name report-writer`. Once the operator has actually sent the submission to the program, set the initial submission status:

      ```bash
      vigil assess finding update <slug> --submission-status submitted --submission-platform <bugcrowd|hackerone|direct> --submission-ref <program report id> --reason "Submitted to <program> on <date>"
      ```

      The first move off `none` must carry `--submission-ref`; the backend rejects a submission state with no referent, and later transitions inherit the stored one. Update as the program responds: `accepted` / `needs_info` / `rejected` / `duplicate` — or `withdrawn` when you retract the report yourself, which also requires `--details-inline '{"withdrawal_reason":"..."}'`. This is independent of `workflow_status` — the finding stays `reported` in the internal record regardless of program outcome. See "Submission Status Lifecycle" in `agent/skills/report-generation/SKILL.md` for the full transition sequence. Once every reportable finding is `reported`, transition phase: `vigil assess transition-phase complete --track web`. The transition gate enforces the recorded-verdict requirement (`kind=missing_blind_triage`); publication before both passes clear creates false workflow state, so keep `reported` transitions behind this gate.
   f. **Internal report — `report.md` (optional, operator-requested):** dispatch only when the operator explicitly wants an operator/client rollup in addition to the per-finding submissions above — it is not required to close out the engagement. Run `vigil assess check-phase-readiness --phase report` first and resolve blockers. Dispatch `report-writer` in draft-generation mode; it queries the backend through `vigil assess finding report --mode final --json` on final reports or `--mode draft --json` on interim reports, plus `attack-chains`, `credentials`, `access-records`, `surfaces`, and `summary` — let it self-serve rather than manually assembling findings context. Draft-generation mode writes `report.md`, runs the consolidated self-review checklist (`agent/skills/report-generation/SKILL.md` "Post-Generation Self-Review" → `agent/references/submission-format.md`), and returns the completed checklist. Dispatch a fresh `report-writer` in review-and-fix mode for `QA PASS`/`QA BLOCKED`, then publish mode: emit `report.generated` and mark included findings `reported` (a no-op if a finding is already `reported` from its own submission). This step is independent of, and does not gate, the per-finding submission closeout above.
   g. **Replies after submission (as needed):** a program comment on an already-submitted finding (typically `submission_status=needs_info`) dispatches `report-writer` in Reply mode, not another full submission pass — see "Reply mode" in `agent/agents/report-writer.md`.
## Definition of Done

The command-checkable readiness gates — Phase-4 verification/workflow queues cleared, severity↔CVSS bands aligned, coverage and root-cause/chain-review state, theoretical-finding disposition — are all enforced by the readiness commands. **Do not re-walk them here by hand.** Run:

- `check-phase-readiness` (the consolidated readiness command) for the per-phase coverage / queue / disposition picture, and
- `vigil assess check-phase-readiness --phase report` for the terminal report gate (it blocks on any report candidate whose `verification_status` is not `confirmed`/`downgraded` — which is what holds a parked theoretical finding out of the report, with no `chain_required` bypass — plus severity↔CVSS mismatch, root-cause groupings, and chain-review state; unlinked markdown notes surface as an advisory, not a blocker, so don't treat one as gating the transition). No readiness path reads `evidence_type`: the label records the confirmation mode, the disposition is what gates.

Resolve every blocker those two report. Restating their checks as a manual checklist was duplicated bureaucracy — the commands are the source of truth, and a hand-checklist drifts from them.

What remains below is **only the judgment that no command can check** — the load-bearing rigor that a passing `check-phase-readiness --phase report` does not, by itself, guarantee. These stay because they are the difference between a clean readiness response and a thorough engagement:

**Run the `phase-qc` skill (`agent/skills/phase-qc/SKILL.md`) at each phase / wind-down boundary — before declaring a surface done, before lifting an account deferral, and before generating the report — to surface these judgment misses systematically.** It is a low-context, ADVISORY critic: it reasons against the coverage ledger (`vigil assess coverage`), the lanes' rendered handoffs, and the findings list (it does NOT recompute coverage or block a transition) and emits a structured miss-list — `{host_or_surface, expected, observed, miss_kind ∈ [coverage, depth, grading, chain, waf-blind], suggested_redispatch}`. It catches the judgment a binary gate cannot ("only the obvious endpoints were hit", "this P4 is impact-if-true a P2", "account-gated but the gate self-mints", "a verdict came off a WAF challenge page"). Consume its miss-list, re-dispatch / re-grade / record-deferral for each row, then re-run it; the judgment boxes below are the misses it is built to find, applied to the report boundary.

- [ ] **Sibling/variant pass per confirmed finding (judgment: was the hunt real).** For each confirmed finding, a completed `variant-rotation` `vulnerability-analyst` dispatch exists against the finding slug — see "Mandatory Phase-Exit Passes" for what the pass must cover and why skipping it is the single most common way real findings are missed in this codebase. The command can confirm the dispatch row exists; only you can confirm the pass *actually hunted* rather than going through the motions.
- [ ] **Chain-construction pass run (judgment: were the chains genuinely sought).** At least one `exploit-developer` pass enumerated A→B candidates across the confirmed set — see "Mandatory Phase-Exit Passes" for the standard chains to check and the `transition-phase report`/`complete` gate that enforces this. Only you can confirm the chains were genuinely constructed rather than a dispatch row going through the motions.
- [ ] **Terminal depth-gate cleared or deliberately deferred (judgment: was "decisive" actually decisive).** A `deep_required` app unit that is decisive-surface or high-confidence is a *deferred-terminal* obligation at TWO grains, not advisory — `transition-phase report`/`complete` blocks with `kind=depth_unsatisfied_units` when the unit was never touched at all for a BLOCK_HIGH family (`access-control`/`auth`/`injection`/`ssrf`/`file`), and separately with `kind=depth_uncovered_classes` when a specific class the unit's gf coverage_items flagged (`signal_classes_uncovered`) was never class-specifically probed — this one fires even when a sibling class already satisfied the family. Clear either by deep-testing the gap, recording a `depth_deferral` decision (`vigil assess agent decision --kind depth_deferral --surfaced-to-user --payload-json '{"host":"<host>","path_prefix":"<prefix>","vuln_classes":[...],"reason":"<why>"}'`), or overriding with `--force --reason "<why>"`. A unit touched-but-family-unfinished, or a non-decisive/low-confidence unit, downgrades to the `kind=depth_under_observed_units` advisory and never blocks — see "Mandatory Phase-Exit Passes" in `agent/operator-core.md` for the full model and the `depth_tier`/`missing (block)`/`missing (warn)`/per-class-signal-gaps vocabulary. Preview the same ledger from Phase 4 on with `check-phase-readiness --by-app-unit` (`--phase report` renders it by default) — the command can confirm the ledger is clean; only you can confirm a cleared unit was actually deep-tested rather than talked past.
- [ ] **Stale-text scrub clean (judgment: prose vs. current state).** Read each active finding's `summary` and `details` text fields and strip phrases that contradict the current state: "severity adjusted from X to Y" when the severity is no longer Y, "originally rated as Z" when the rating has shifted twice since, "merged from W" when W has since been split off, "downgraded to medium" / "upgraded to high" / "previously low" against the current severity field. Stale narrative is invisible to backend status fields and ends up in `submission.md` (or `report.md`, if generated) verbatim. The `vigil assess finding list --json | jq -r .[].slug` loop in `agent/skills/report-generation/SKILL.md` Review-and-Fix QA Mode is the executable recipe. A CVSS-band check passes this; reading the prose is the only way to catch it.
- [ ] **Debate-skipped runtime-proven findings passed the FP & severity gate (judgment: real-object impact).** Per `agent/references/finding-fp-and-severity-gate.md`, every confirmed runtime-proven finding that skipped the Ideator-vs-Tracer debate (data-exposure, write-impact, auth-bypass, race, business-logic) has a recompute-checked CVSS vector, a proven real-object impact (a read-back, not an orphan write), and a recorded enumerability assessment in `details`. This is the C1–C7 judgment a band check cannot make.
- [ ] **Current reproduction check.** The latest `repro_rehearsal` decision is `followed`, or `equivalent` from a fresh reviewer with a cited prior successful check, and covers the current steps and ordered run IDs. Final export checks this digest; you still judge whether the tester really observed the claimed outcome by following the steps without author context.
- [ ] **Current blind review.** Every Medium-or-above submission has a recorded `Accept@P*` with its `packet_id` and actual reviewer/writer dispatch attribution. The reviewer differs from the finding author and report writer. Final export checks the latest verdict against the actual external body, attachments, platform, brief, and rubric. You still judge whether the fresh reviewer honored the packet-only boundary.
- [ ] **Cross-finding dedup / lead-selection pass run (judgment: no self-inflicted duplicates).** Before submitting any cluster of ≥2 findings that share a root cause, an explicit cross-finding pass (`agent/rules/reporting.md` §18 "Cross-finding dedup pass") clustered the submittable set, designated the **lead** (highest-impact) finding, and for each dup-risk sibling recorded either a consolidation or a distinct-primitive framing plus `finding link --root-cause`. Blind Pass-2 triage is per-finding and structurally cannot catch this — it never sees the cluster — and the per-surface hunt never sees it either, so this is a separate operator responsibility at report time. The failure mode is filing a P3 read and a P2 write on one broken endpoint family as two independent tickets and having the read dup-closed into the write. Only you can confirm the cluster was actually reconciled rather than N findings filed independently on one control.
- [ ] **Backend reflects submissions (external reality).** Findings actually submitted to the program (or marked accepted/duplicate) have a workflow status that matches reality; nothing remains "draft" if it was sent out. No command can observe the program's side — only you can reconcile it.

**Wind-down re-collection cue.** Before declaring the hunt done and entering the report phase, re-run collection (a fresh `vigil assess recon` / `surface-collector` pass over the apexes) rather than trusting the stale work buffer — a fresh pass is cheap relative to a missed finding; stale buffers hide live handler paths that surfaced after the Phase 2 crawl.

When `check-phase-readiness --phase report` is clean AND the judgment items above hold, dispatch `report-writer` for the final pass and then close the engagement.
