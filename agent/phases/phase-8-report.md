# Phase 8 — Report

**Read-on-phase-entry.** Read this doc once `vigil assess check-phase-readiness` shows the phases through Exploit clear ("Phase Index" in `AGENTS.md`), and again on a method re-anchor. It carries the author → QC → cold reproduction → blind triage → publish flow for the **default per-finding submission closeout** (android uses the same flow), the optional internal `report.md`, and the **Definition of Done**: the judgment no command can check.

8. **REPORT** → keep reporting inside the existing `report` phase. **Per-finding submissions are the default closeout.** Each finding moves through authoring, independent QC, a cold reproduction and claim check, blind triage, and publish, so every review judges the same final bytes before lifecycle state changes. The internal `report.md` (step f) is optional and operator-requested; it does not gate or substitute for the per-finding closeout below.

   **Before drafting anything — readiness and ticket count.** Run `vigil assess check-phase-readiness --phase report` and resolve its blockers. Then decide the ticket count ONCE across the whole reportable set: re-drafting after a dup-close wastes the submission, and splitting a root cause across two tickets under-states its blast radius. Blind triage judges one finding's bytes and never sees the cluster, and the per-surface hunt never sees it either, so this cross-finding pass is yours:

   1. **Cluster by root cause** — group findings that share the same vulnerable control, component, or endpoint family (not merely the same host). A shared *selector* — every handler trusting the same client-supplied `userId`/`id` — is a cluster signal.
   2. **Pick the lead** — the highest-impact finding in the cluster is the canonical submission and carries the cluster's severity. A cross-user *write* leads a cross-user *read*; an RCE leads the info-leak that enabled it.
   3. **Consolidate or separate.** **Same endpoint family + same selector/object class → high dup risk:** consolidate into the lead as "root cause + all demonstrated impacts" (`agent/rules/reporting.md` Rule 18), or, if filing separately, frame each sibling by its *distinct primitive* (the read is the discovery/harvest primitive; the write is the tampering primitive). **Different endpoint + different object + different authority/impact axis → low dup risk:** file separately.
   4. **Record the decision** with `vigil assess finding link <sibling> --root-cause <lead>`, and pick `--effect` by a separate question — **would the same programmatic fix resolve both?** Answer from where the fix would land in the code, not from how similar the findings look: a read and a write on one broken endpoint are usually one fix, and two endpoints missing the same check are one fix when the check lives in shared code and two when it does not. Note the lead-vs-sibling framing in each finding's notes so the decision is not re-litigated.
      - **Distinct fixes → `eliminates_attack_path`**, the default. The sibling survives the root fix as its own remediation item, and the link disturbs no verdict. Use it even when step 3 consolidated: one ticket to the program can still be two fixes in the code.
      - **One fix → `--effect eliminates_finding`.** This raises a claim review on a confirmed or downgraded sibling and a `finding_claim_review_pending` blocker; step c settles it.

   Review the clusters with `vigil assess finding list --root-cause <root-slug>`. `check-phase-readiness --phase report` surfaces the clusters it can see; the same-fix judgement is not inferable from the finding rows.

   a. **Author (writer dispatch W, per finding):** dispatch `report-writer` in submission authoring mode with `--platform <bugcrowd|hackerone|direct|ghsa>` (`direct` when there is no bug-bounty program). W runs `agent/agents/report-writer.md` "Mandatory Closing Sequence" and hands back a `vigil assess export triage-packet <slug>` built with exactly the attachments intended for delivery; its `export submission --draft` renders record W as the workspace's writer, so QC can refuse a reviewer that wrote it. W records no decision; it hands back the `packet_id`, its dispatch ID, and the pending reviews. An empty or unbindable `steps_to_reproduce` is `QA BLOCKED`, and the finding goes back to the specialist that held the session.

   b. **Independent QC (report-writer dispatch Q):** dispatch a separate `report-writer` in submission QC mode with the packet. Q reviews only and records `vigil assess agent decision --kind submission_qc_verdict` for that packet; `vigil assess contract agent decision` owns the payload.
      - A QC objection blocks only when it cites a failing checklist row, the fabrication boundary, or the verbatim-evidence rule, with the offending quote. Anything else is advisory.
      - `blocked` → re-dispatch W with the failed rows; W repairs at the finding and builds a new packet, then a QC dispatch reviews the new packet.
      - The same row failing again after one repair → decide it yourself rather than looping.
      - Evidence or severity objections → the specialist that holds the finding, since W cannot repair them.

   c. **Cold reproduction, then claim check (verifier dispatch V):** after QC passes, dispatch a fresh `vulnerability-analyst` for live findings, `code-vuln-verifier` for findings whose `reproduction_basis` is `source`, or `code-fuzz-engineer` for fuzz/crash findings.
      - **Rehearse first, cold.** The dispatch context carries only `details.steps_to_reproduce` and `details.repro_runs` — no summary, author handoff, or chain narrative — so V tests whether a stranger can follow the steps. Success means V followed the authored steps and observed the claimed outcome; a zero exit code alone is insufficient. Live and fuzz checks cite every authored `repro_runs` ID plus at least one completed V command run; source checks name the independently observed source result. V records `vigil assess agent decision --kind repro_rehearsal` with its own dispatch ID.
      - **Then the claim.** If finding GET shows `verification_audit.claim_review_pending`, V reads the finding and records `claim_equivalence` with the transition ID and digest from that GET. `code-fuzz-engineer` is not a claim-equivalence role, so a fuzz finding's pending claim review takes a separate `code-vuln-verifier` dispatch. An equivalent claim clears the review; `changed` returns the finding for terminal verification.
      - `failed` → the specialist that held the session, with the exact step and breakage. Never to the writer, which cannot run probes and could only paper over the gap with plausible prose.
      - The rehearsal digest covers the current steps and ordered run IDs. A later step edit makes it stale: a fresh V re-rehearses, or, for a wording-only change, records `verdict=equivalent` citing the prior `followed` decision as the contract describes.

   d. **Blind pre-submission triage (Pass 2):** every **Medium-or-above** submission gets a fresh `blind-reviewer` review of the same packet, per `agent/skills/blind-triage/SKILL.md`. Give the reviewer only the packet's external `submission.md`, attachments, program brief, and rubric. Record its verdict with the packet's `packet_id`: `vigil assess agent decision --kind blind_triage_verdict --payload-json '{"finding_slug":"<slug>","packet_id":"<64-char packet id>","reviewer_dispatch_agent_id":"<reviewer-id>","writer_dispatch_agent_id":"<writer-id>","verdict":"<Accept@P1..P5|Need-More-Info|Not-Applicable-Informational|Out-of-Scope|Duplicate>"}'`. A non-Accept result goes to W for repair; the repaired packet goes back through b, through c for whatever the repair touched, and a new blind pass.

   e. **Publish (per finding):** once QC, rehearsal, claim review, and (Medium+) blind triage are current for the packet, publish through a separate `report-writer` publish dispatch or run it yourself. `export submission <slug> --platform <same> --prepare` checks the final gate without publishing; the publish itself is `vigil assess export submission <finding-slug> --platform <same platform>` with the packet's attachments (the captured `--body` / `--guidance` are reused), without `--draft` or `--prepare`. Final mode enforces the executable gate documented by `vigil assess contract export submission`; resolve any non-zero diagnostic at the finding instead of bypassing it. Only after it exits 0, mark the finding: `vigil assess finding update <slug> --status reported --reason "Submission cleared for delivery" --source-name report-writer`, adding `--agent-id <publisher-id>` when a report-writer dispatch runs it. Once you have actually sent the submission to the program, set the initial submission status:

      ```bash
      vigil assess finding update <slug> --submission-status submitted --submission-platform <bugcrowd|hackerone|direct|ghsa> --submission-ref <program report id> --reason "Submitted to <program> on <date>"
      ```

      The first move off `none` must carry `--submission-ref`; later transitions inherit it. "Submission Status Lifecycle" in `agent/skills/report-generation/SKILL.md` owns the full transition sequence. Once every reportable finding is `reported`, transition phase: `vigil assess transition-phase complete --track web` (the code track closes with its own gates in `agent/phases/code-phase-4-fuzz.md`). The transition gate enforces the recorded verdicts (`missing_blind_triage`, `missing_submission_qc`, and `missing_report_qc` when `report.md` is registered), so keep `reported` transitions behind the reviews above.
   f. **Internal report — `report.md` (optional, operator-requested):** dispatch only when the operator wants an operator/client rollup in addition to the per-finding submissions above. Dispatch `report-writer` in draft mode; it queries the backend itself (`vigil assess finding report --mode final --json`, or `--mode draft --json` on interim reports, plus attack chains, credentials, access records, surfaces, and summary), runs the stale-text scrub and self-review, and registers `report.md`. Then dispatch a separate `report-writer` in QC mode, which records `report_qc_verdict` for those bytes, and publish after a pass: emit `report.generated` and mark `reported` only the included findings that have no per-finding submission workspace, because `report.md` is their deliverable; a finding with a submission workspace becomes `reported` through its own exit-0 final export in step e. This step does not gate the per-finding closeout above.
   g. **Replies after submission (as needed):** a program comment on an already-submitted finding (typically `submission_status=needs_info`) dispatches `report-writer` in reply mode, not another submission pass — see "Closing verbs (reply mode)" in `agent/agents/report-writer.md`.

## Definition of Done

The readiness commands enforce everything checkable — verification and workflow queues, coverage,
root-cause and chain-review state, theoretical-finding disposition, and the recorded QC, rehearsal
and blind-triage verdicts at `complete` — and name the rest as advisories (severity↔CVSS
divergence among them, which submission QC also reads). Resolve every blocker
`vigil assess check-phase-readiness --phase report` names and do not re-walk its checks by hand. It
blocks any report candidate whose `verification_status` is not `confirmed`/`downgraded`, which is what
holds a parked theoretical finding out of the report; no readiness path reads `evidence_type`.

Run the `phase-qc` skill (`agent/skills/phase-qc/SKILL.md`) at each phase and wind-down boundary and
before the report. It is an advisory critic over the coverage ledger, the lanes' handoffs and the
findings list, and emits a miss-list (`coverage`, `depth`, `grading`, `chain`, `waf-blind`) with a
suggested re-dispatch per row; act on each row and re-run it. What remains is judgment:

- [ ] **The variant/sibling pass really hunted** (web track). The gate sees a completed `variant-rotation` row per confirmed finding; only you can tell whether it hunted the adjacent routes, controllers, content types and auth contexts or went through the motions.
- [ ] **Chains were genuinely sought** (web track). An `exploit-developer` pass enumerated A→B candidates across the confirmed set ("Mandatory Phase-Exit Passes" in `agent/operator-core.md`), and each advisory-named unchained high/critical finding was considered.
- [ ] **A cleared depth unit was deep-tested, not talked past** (web track). Decisive or high-confidence `deep_required` units clear by deep testing, a recorded `depth_deferral` (`vigil assess agent decision --kind depth_deferral --surfaced-to-user --payload-json '{"host":"<host>","path_prefix":"<prefix>","vuln_classes":[...],"reason":"<why>"}'`), or `--force --reason`; `check-phase-readiness --by-app-unit` shows the ledger.
- [ ] **Finding prose matches current state.** Read each active finding's `summary` and `details` text and strip phrases that contradict it ("severity adjusted from X to Y" when it is no longer Y, "merged from W" after W was split off, "downgraded to medium" against the current field). Stale narrative reaches `submission.md` verbatim; `agent/skills/report-generation/SKILL.md` "Stale-text scrub" is the recipe.
- [ ] **Runtime-proven findings that skipped the debate passed the FP & severity gate.** Per `agent/references/finding-fp-and-severity-gate.md`, each confirmed data-exposure, write-impact, auth-bypass, race or business-logic finding has a recompute-checked CVSS vector, a proven real-object impact (a read-back, not an orphan write) and a recorded enumerability assessment.
- [ ] **The reviews were real.** Each QC blocking row cited a genuine checklist failure; the latest rehearsal followed the steps cold and observed the claimed outcome; each blind reviewer honored the packet-only boundary and differs from the author and writer.
- [ ] **No self-inflicted duplicates.** Before submitting any cluster that shares a root cause, the cross-finding pass at the top of step 8 picked the lead and recorded consolidation or distinct-primitive framing plus `finding link --root-cause` for each sibling. Blind triage is per finding and cannot see the cluster.
- [ ] **The backend reflects external reality.** Findings sent to the program (or marked accepted/duplicate) carry a matching workflow and submission status; nothing sent out remains `draft`.

When `check-phase-readiness --phase report` is clean, every reportable finding is published through
steps a-e, and the judgment items above hold, close the engagement.
