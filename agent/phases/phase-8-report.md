# Phase 8 — Report

**Read-on-phase-entry.** When you ENTER Phase 8, Read this doc; re-read it on a method re-anchor. **Per the Core Loop re-anchor scoping, do NOT read this doc during Phases 1–6** — the Report walkthrough and the Definition of Done below are report-time judgment, and re-reading them mid-run is exactly the reporting-prematurity bleed that scoping prevents. Read it only once `vigil assess check-phase-readiness` shows the pre-report phases (through Exploit) clear. It carries the draft → targeted-evidence → checklist/QA → blind-triage → publish gate for the **default per-finding submission closeout** (android runs this same core and this same report flow — there is no separate android core), the optional internal-report mode, and the **Definition of Done** (the judgment-only closeout that no command can check). Cross-phase machinery stays in `AGENTS.md`.

8. **REPORT** → keep reporting inside the existing `report` phase. **Per-finding submissions are the default closeout** — use a draft → targeted-evidence → checklist/QA → blind-triage → publish gate per finding so each submission is reviewed before lifecycle state changes. The internal `report.md` (step f) is optional and operator-requested; it does not gate or substitute for the per-finding closeout below.
   a. **Scaffold (per finding, default):** for each reportable finding, dispatch `report-writer` in submission mode: `vigil assess export submission <finding-slug> --platform <bugcrowd|hackerone|direct> --draft`. This renders `$ENGAGEMENT_DIR/submissions/<slug>/submission.md` + `submission-context.json` FROM the finding's own fields (the finding is the source of truth) and consolidates the finding metadata, any hygiene warnings, the structured proof, and every linked command run into ONE "OPERATOR DETAILS — NOT FOR SUBMISSION" reference section below the second `---` (present in both draft and final; never pasted) — report-writer authors the body sections FROM what the command produces, it does not hand-assemble the draft. `--draft` never sets `submission_status`; it does not emit any event or mark the finding `reported`.
   b. **Author + write back to the finding (same dispatch):** report-writer authors the stable sections (Summary, Steps to Reproduce, Evidence, optional Attack Scenario, Impact, Remediation), resolving every `[NEEDS: ...]` marker with real backend-sourced content (title, severity + CVSS vector, platform taxonomy, attacker-impact statement, concrete proof), and writes each section BACK to the finding so it holds exactly what would be sent — `vigil assess finding update <slug> --summary "..." --details-inline '{"steps_to_reproduce":[...],"evidence":"...","impact":"...","remediation":"..."}'`. **Evidence is authored, not tool-dumped:** report-writer builds it from the OPERATOR DETAILS section's structured proof and linked command runs PLUS a targeted `vigil assess command-run list --q "<the finding's specific url/param/header/uri>"` (`--show-matches` / `--all` as needed) to catch reproducing runs the linked set missed, links any it finds (`vigil assess finding link <slug> --link-kind evidence --target-kind command_run --target-id <run_id>` — durable reference), then masks PII and annotates the proof lines and stores that authored Evidence in `details.evidence`. Authored prose and inline PoC remain supporting material; satisfy the durable-proof requirement shown by `vigil assess contract export submission`. Verify a verb before citing it through `vigil assess list-commands --grep <term>` or its contract.
   c. **Checklist/QA (Pass 1 — in-context):** report-writer re-renders from the finding (`vigil assess export submission <slug> --platform <same> --draft --overwrite`) and runs the one consolidated pre-submission / report QA checklist in `agent/references/submission-format.md` against the re-rendered `submission.md` — the same checklist SKILL.md's "Post-Generation Self-Review" points to (PII redaction, internal identifiers, mandatory fields, banned phrasing per `agent/rules/reporting.md` Rule 20), fixes what it can at the SOURCE (the finding, then re-render — a fix made only in `submission.md` is lost on the next render), and returns `QA PASS` or `QA BLOCKED` with the exact gap and required operator action. This is the first of the two-pass gate: full context, fixes the finding; it does not reliably catch whether impact was actually demonstrated.
   d. **Blind pre-submission triage (Pass 2 — zero-context, decisive):** every **Medium-or-above** submission gets a BLIND triage before publish — the operator runs this review pattern using `agent/skills/blind-triage/SKILL.md`. Dispatch a **non-specialist general agent** (strongest model, no engagement skills, no engagement context) and give it ONLY the program brief facts (in-scope assets, triage bar, severity-band policy) plus the submission bytes — under hard isolation: it reads ONLY the submission `.md` and runs no repo file read, no `vigil`/CLI/curl command, and no work-buffer access. It judges the bytes like a real Bugcrowd triager and returns a structured verdict (`Accept@P1..P5` / `Need-More-Info` / `Not-Applicable-Informational` / `Out-of-Scope` / `Duplicate`), priority-vs-claimed-severity, triage reasoning, and weak points. **Record the verdict before publish** — the verdict is durable, not advisory: for each Medium-or-above finding, persist it with `vigil assess agent decision --kind blind_triage_verdict --payload-json '{"finding_slug":"<slug>","verdict":"<Accept@Px|Need-More-Info|Not-Applicable|Out-of-Scope|Duplicate>","claimed_severity":"<sev>","weak_points":"..."}'`. `transition-phase report`/`complete` reads these rows and blocks (`kind=missing_blind_triage`) for any Medium-or-above active finding lacking a recorded `Accept` verdict, so an un-recorded verdict is treated as no triage at all. **Gating rule:** anything other than `Accept` blocks submission — route the finding back to the report-writer/operator, fix the gap, and re-run the blind pass (recording the new verdict); only `Accept` clears it. This is an operator-run review pattern, not a roster role — the zero-context blindness is the whole point, so it stays operator-run rather than a registered specialist that would carry engagement context.
   e. **Publish (per finding):** only after `QA PASS` (Pass 1) AND, for Medium-or-above findings, a recorded `Accept` blind verdict (Pass 2), re-run `vigil assess export submission <finding-slug> --platform <same platform> --overwrite` **without** `--draft`. Final mode enforces the executable gate documented by `vigil assess contract export submission`; resolve any non-zero diagnostic at the finding instead of bypassing it. It never sets `submission_status`. Then mark the finding lifecycle: `vigil assess finding update <slug> --status reported --reason "Submission cleared for delivery" --source-name report-writer`. Once the operator has actually sent the submission to the program, set the initial submission status:

      ```bash
      vigil assess finding update <slug> --submission-status submitted --reason "Submitted to <program> on <date>"
      ```

      Update as the program responds: `accepted` / `needs_info` / `rejected` / `duplicate`. This is independent of `workflow_status` — the finding stays `reported` in the internal record regardless of program outcome. See "Submission Status Lifecycle" in `agent/skills/report-generation/SKILL.md` for the full transition sequence. Once every reportable finding is `reported`, transition phase: `vigil assess transition-phase complete --track web`. The transition gate enforces the recorded-verdict requirement (`kind=missing_blind_triage`); publication before both passes clear creates false workflow state, so keep `reported` transitions behind this gate.
   f. **Internal report — `report.md` (optional, operator-requested):** dispatch only when the operator explicitly wants an operator/client rollup in addition to the per-finding submissions above — it is not required to close out the engagement. Run `vigil assess check-phase-readiness --phase report` first and resolve blockers. Dispatch `report-writer` in draft-generation mode; it queries the backend through `vigil assess finding report --mode final --json` on final reports or `--mode draft --json` on interim reports, plus `attack-chains`, `credentials`, `access-records`, `surfaces`, and `summary` — let it self-serve rather than manually assembling findings context. Draft-generation mode writes `report.md`, runs the consolidated self-review checklist (`agent/skills/report-generation/SKILL.md` "Post-Generation Self-Review" → `agent/references/submission-format.md`), and returns the completed checklist. Dispatch a fresh `report-writer` in review-and-fix mode for `QA PASS`/`QA BLOCKED`, then publish mode: emit `report.generated` and mark included findings `reported` (a no-op if a finding is already `reported` from its own submission). This step is independent of, and does not gate, the per-finding submission closeout above.
   g. **Replies after submission (as needed):** a program comment on an already-submitted finding (typically `submission_status=needs_info`) dispatches `report-writer` in Reply mode, not another full submission pass — see "Reply mode" in `agent/agents/report-writer.md`.
## Definition of Done

The command-checkable readiness gates — Phase-4 verification/workflow queues cleared, severity↔CVSS bands aligned, coverage and root-cause/chain-review state, theoretical-finding disposition — are all enforced by the readiness commands. **Do not re-walk them here by hand.** Run:

- `check-phase-readiness` (the consolidated readiness command) for the per-phase coverage / queue / disposition picture, and
- `vigil assess check-phase-readiness --phase report` for the terminal report gate (it blocks on unreviewed findings, severity↔CVSS mismatch, root-cause groupings, chain-review state, and theoretical-without-`chain_required` disposition; unlinked markdown notes surface as an advisory, not a blocker, so don't treat one as gating the transition).

Resolve every blocker those two report. Restating their checks as a manual checklist was duplicated bureaucracy — the commands are the source of truth, and a hand-checklist drifts from them.

What remains below is **only the judgment that no command can check** — the load-bearing rigor that a passing `check-phase-readiness --phase report` does not, by itself, guarantee. These stay because they are the difference between a clean readiness response and a thorough engagement:

**Run the `phase-qc` skill (`agent/skills/phase-qc/SKILL.md`) at each phase / wind-down boundary — before declaring a surface done, before lifting an account deferral, and before generating the report — to surface these judgment misses systematically.** It is a low-context, ADVISORY critic: it reasons against the coverage ledger (`vigil assess coverage`), the lanes' rendered handoffs, and the findings list (it does NOT recompute coverage or block a transition) and emits a structured miss-list — `{host_or_surface, expected, observed, miss_kind ∈ [coverage, depth, grading, chain, waf-blind], suggested_redispatch}`. It catches the judgment a binary gate cannot ("only the obvious endpoints were hit", "this P4 is impact-if-true a P2", "account-gated but the gate self-mints", "a verdict came off a WAF challenge page"). Consume its miss-list, re-dispatch / re-grade / record-deferral for each row, then re-run it; the judgment boxes below are the misses it is built to find, applied to the report boundary.

- [ ] **Sibling/variant pass per confirmed finding (judgment: was the hunt real).** For each confirmed finding, a completed `variant-rotation` `vulnerability-analyst` dispatch exists against the finding slug — see "Mandatory Phase-Exit Passes" for what the pass must cover and why skipping it is the single most common way real findings are missed in this codebase. The command can confirm the dispatch row exists; only you can confirm the pass *actually hunted* rather than going through the motions.
- [ ] **Chain-construction pass run (judgment: were the chains genuinely sought).** At least one `exploit-developer` pass enumerated A→B candidates across the confirmed set — see "Mandatory Phase-Exit Passes" for the standard chains to check and the `transition-phase report`/`complete` gate that enforces this. Only you can confirm the chains were genuinely constructed rather than a dispatch row going through the motions.
- [ ] **Terminal depth-gate cleared or deliberately deferred (judgment: was "decisive" actually decisive).** A `deep_required` app unit that is decisive-surface or high-confidence is a *deferred-terminal* obligation at TWO grains, not advisory — `transition-phase report`/`complete` blocks with `kind=depth_unsatisfied_units` when the unit was never touched at all for a BLOCK_HIGH family (`access-control`/`auth`/`injection`/`ssrf`/`file`), and separately with `kind=depth_uncovered_classes` when a specific class the unit's gf coverage_items flagged (`signal_classes_uncovered`) was never class-specifically probed — this one fires even when a sibling class already satisfied the family. Clear either by deep-testing the gap, recording a `depth_deferral` decision (`vigil assess agent decision --kind depth_deferral --surfaced-to-user --payload-json '{"host":"<host>","path_prefix":"<prefix>","vuln_classes":[...],"reason":"<why>"}'`), or overriding with `--force --reason "<why>"`. A unit touched-but-family-unfinished, or a non-decisive/low-confidence unit, downgrades to the `kind=depth_under_observed_units` advisory and never blocks — see "Mandatory Phase-Exit Passes" in `agent/operator-core.md` for the full model and the `depth_tier`/`missing (block)`/`missing (warn)`/per-class-signal-gaps vocabulary. Preview the same ledger from Phase 4 on with `check-phase-readiness --by-app-unit` (`--phase report` renders it by default) — the command can confirm the ledger is clean; only you can confirm a cleared unit was actually deep-tested rather than talked past.
- [ ] **Stale-text scrub clean (judgment: prose vs. current state).** Read each active finding's `summary` and `details` text fields and strip phrases that contradict the current state: "severity adjusted from X to Y" when the severity is no longer Y, "originally rated as Z" when the rating has shifted twice since, "merged from W" when W has since been split off, "downgraded to medium" / "upgraded to high" / "previously low" against the current severity field. Stale narrative is invisible to backend status fields and ends up in `submission.md` (or `report.md`, if generated) verbatim. The `vigil assess finding list --json | jq -r .[].slug` loop in `agent/skills/report-generation/SKILL.md` Review-and-Fix QA Mode is the executable recipe. A CVSS-band check passes this; reading the prose is the only way to catch it.
- [ ] **Debate-skipped runtime-proven findings passed the FP & severity gate (judgment: real-object impact).** Per `agent/references/finding-fp-and-severity-gate.md`, every confirmed runtime-proven finding that skipped the Ideator-vs-Tracer debate (data-exposure, write-impact, auth-bypass, race, business-logic) has a recompute-checked CVSS vector, a proven real-object impact (a read-back, not an orphan write), and a recorded enumerability assessment in `details`. This is the C1–C7 judgment a band check cannot make.
- [ ] **Blind pre-submission triage passed AND recorded (judgment: would an outside triager accept it).** Every Medium-or-above submission cleared the BLIND Pass-2 triage (`agent/skills/blind-triage/SKILL.md`) with an `Accept` verdict, and that verdict is **recorded** via `vigil assess agent decision --kind blind_triage_verdict --payload-json '{"finding_slug":"<slug>","verdict":"Accept@Px",...}'` before publish — see the Report phase step `d`. The `transition-phase report`/`complete` gate blocks (`kind=missing_blind_triage`) on any Medium-or-above active finding without a recorded `Accept` verdict, so an un-recorded verdict reads as no triage at all. A non-`Accept` blind verdict is a block, not an advisory; only you can confirm the zero-context reviewer actually judged the bytes rather than being fed engagement context.
- [ ] **Cross-finding dedup / lead-selection pass run (judgment: no self-inflicted duplicates).** Before submitting any cluster of ≥2 findings that share a root cause, an explicit cross-finding pass (`agent/rules/reporting.md` §18 "Cross-finding dedup pass") clustered the submittable set, designated the **lead** (highest-impact) finding, and for each dup-risk sibling recorded either a consolidation or a distinct-primitive framing plus `finding link --root-cause`. Blind Pass-2 triage is per-finding and structurally cannot catch this — it never sees the cluster — and the per-surface hunt never sees it either, so this is a separate operator responsibility at report time. The failure mode is filing a P3 read and a P2 write on one broken endpoint family as two independent tickets and having the read dup-closed into the write. Only you can confirm the cluster was actually reconciled rather than N findings filed independently on one control.
- [ ] **Backend reflects submissions (external reality).** Findings actually submitted to the program (or marked accepted/duplicate) have a workflow status that matches reality; nothing remains "draft" if it was sent out. No command can observe the program's side — only you can reconcile it.

**Wind-down re-collection cue.** Before declaring the hunt done and entering the report phase, re-run collection (a fresh `vigil assess recon` / `surface-collector` pass over the apexes) rather than trusting the stale work buffer — a fresh pass is cheap relative to a missed finding; stale buffers hide live handler paths that surfaced after the Phase 2 crawl.

When `check-phase-readiness --phase report` is clean AND the judgment items above hold, dispatch `report-writer` for the final pass and then close the engagement.
