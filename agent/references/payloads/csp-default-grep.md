# Vendor-Template CSP / CORS Re-Baseline — Default Grep

> Source: Custom — compiled from vendor production-hardening checklists and template-default research.

When a vendor product fingerprint matches (Salesforce Communities, ServiceNow, Drupal, Pexip Infinity, generic Cisco / appliance vendors, off-the-shelf SaaS), re-pull the response headers and grep for placeholder literals from the vendor's installer template. Vendors ship CSP / CORS / Feature-Policy directives with `https://example.com` style placeholders that operators are expected to replace; the placeholder surviving into production is a misconfiguration in its own right and a strong indicator that the deployment did not run the vendor's hardening guide.

This re-baseline check fires AFTER the initial recon-pass headers have been captured. The first pass establishes the deployment exists; the re-baseline check examines whether the headers reflect the vendor's hardened defaults or the installer-template defaults.

## Placeholder-literal grep pattern

The literals below are documented placeholder values in vendor installer templates. A live deployment that ships any of these in a CSP or CORS directive is running the installer-default policy, not a hardened policy.

```bash
# Save the headers from the recon pass to a file first
aith assess kali exec --technique INFO-DISCLOSURE \
  --intent "vendor-template CSP/CORS re-baseline header capture" \
  --probe-kind fingerprint --phase recon --timeout 30 -- \
  curl -sSI 'https://TARGET/' \
  > /engagements/$ENGAGEMENT_KEY/scans/headers_TARGET.txt

# Grep for the placeholder set
grep -inE \
  'example\.com|example\.org|example\.net|example\.test|domain-here\.tld|your-domain\.tld|your\.domain|placeholder|change-?me|REPLACE_ME|TODO|FIXME|localhost|127\.0\.0\.1|0\.0\.0\.0|::1' \
  /engagements/$ENGAGEMENT_KEY/scans/headers_TARGET.txt
```

Match in any of these directives:

- `Content-Security-Policy`, `Content-Security-Policy-Report-Only`
- `Access-Control-Allow-Origin`, `Access-Control-Allow-Headers`, `Access-Control-Expose-Headers`
- `Feature-Policy`, `Permissions-Policy`
- `X-Frame-Options` (where `ALLOW-FROM <url>` is still in use)
- `Strict-Transport-Security` (max-age=0 indicates a placeholder defer)
- Custom header redirects in `Location:` chains where placeholders appear

A hit is not always a finding by itself, but it is always evidence that the vendor's hardening checklist was not run — record an intel-note even when the placeholder appears in a directive that does not directly affect attack surface, because the same operator process probably skipped other hardening items too.

## Unsafe-inline + unsafe-eval combination check

The `'unsafe-inline'` and `'unsafe-eval'` source-list values in `script-src` defeat CSP's primary purpose. Either alone is a yellow flag; both together inside a single `script-src` directive is a red flag that the policy was generated by a template that aimed to be permissive enough not to break anything, not to block XSS:

```bash
grep -iE 'script-src[^;]*unsafe-inline[^;]*unsafe-eval|script-src[^;]*unsafe-eval[^;]*unsafe-inline' \
  /engagements/$ENGAGEMENT_KEY/scans/headers_TARGET.txt
```

Both values surviving into production usually indicates that the operator pasted the vendor-default `script-src` from the installer documentation without running the per-app source audit the documentation also prescribed.

## Overly-broad wildcard check

Some vendors publish CSPs that wildcard a full vendor domain or cloud-provider domain. The wildcards are convenient for the vendor's CI but expose the policy to lateral subdomain takeover and same-origin chained attacks:

```bash
grep -iE \
  'script-src[^;]*(\*\.amazonaws\.com|\*\.cloudfront\.net|\*\.azurewebsites\.net|\*\.windows\.net|\*\.googleusercontent\.com|\*\.appspot\.com|\*\.herokuapp\.com|\*\.netlify\.app)|script-src[^;]*\bhttps?:\b|script-src[^;]*data:|script-src[^;]*blob:' \
  /engagements/$ENGAGEMENT_KEY/scans/headers_TARGET.txt
```

`https:` alone (no domain restriction) and `data:` / `blob:` in `script-src` are the highest-impact misconfigurations. Record each as a separate finding when no compensating control narrows the source.

## Per-vendor known-default snippets

These snippets are published in vendor installer / hardening documentation as the *unhardened* default. Match the exact directive shape and record an intel-note per match (the lesson is "the operator did not run the hardening checklist," not the specific directive).

### Salesforce Communities (Lightning) — pre-hardening default

```
Content-Security-Policy: default-src 'self' *.force.com *.salesforce.com *.salesforce-communities.com data: blob:; script-src 'self' 'unsafe-inline' 'unsafe-eval' *.force.com *.salesforce.com; style-src 'self' 'unsafe-inline' *.force.com *.salesforce.com; img-src 'self' data: blob: *
```

The trailing `*` on `img-src`, `unsafe-inline` + `unsafe-eval` on `script-src`, and the broad `*.salesforce.com` wildcard are the installer defaults. Salesforce's hardening guide replaces the wildcards with explicit Experience Cloud subdomains.

### ServiceNow — pre-hardening default

```
Content-Security-Policy: default-src 'self' *.service-now.com; script-src 'self' 'unsafe-inline' 'unsafe-eval' *.service-now.com; img-src 'self' data: *
```

ServiceNow hardening adds explicit nonces to `script-src` and removes the trailing `*` on `img-src`. The pre-hardening default ships when the instance is first provisioned.

### Drupal — pre-hardening default

The Security Kit (`seckit`) module ships with a permissive sample CSP that maintainers are expected to tighten:

```
Content-Security-Policy: default-src 'self'; script-src 'self' 'unsafe-inline' 'unsafe-eval'; style-src 'self' 'unsafe-inline'; img-src 'self' data: https:; report-uri https://example.com/csp-report
```

The `report-uri https://example.com/...` directive is the placeholder that ships with the module's example config; surviving into production confirms the module is running its sample policy.

### Pexip Infinity — pre-hardening default

The Conferencing Node administration UI publishes:

```
Content-Security-Policy: default-src 'self'; script-src 'self' 'unsafe-inline'; img-src 'self' data:; connect-src 'self' wss://*.example.com
```

The `connect-src wss://*.example.com` is the installer default for the WebSocket signaling endpoint. Replace with the actual conferencing-node FQDN during hardening; the placeholder surviving means the WebSocket signaling will fail to negotiate (or the policy is in `Report-Only` mode and not enforced).

### Cisco appliance / network-management UI — pre-hardening default

Many Cisco management UIs ship CSPs that allow `data:` and `blob:` in `script-src` for the embedded policy editor:

```
Content-Security-Policy: default-src 'self'; script-src 'self' 'unsafe-inline' 'unsafe-eval' data: blob:; img-src 'self' data:
```

`data:` and `blob:` in `script-src` are an immediate XSS-amplification hazard.

## Bash helper — sweep across a list of header dumps

When the recon pass captured headers for many hosts, the helper below runs the placeholder-literal grep and the unsafe-inline + unsafe-eval check across the full set in one pass:

```bash
#!/usr/bin/env bash
# csp-default-grep.sh — sweep header dumps for vendor-template placeholders.
# Usage: csp-default-grep.sh /engagements/$ENGAGEMENT_KEY/scans/headers_*.txt

set -euo pipefail

PLACEHOLDER_RE='example\.(com|org|net|test)|domain-here\.tld|your-domain\.tld|your\.domain|placeholder|change-?me|REPLACE_ME|TODO|FIXME|localhost|127\.0\.0\.1|0\.0\.0\.0|::1'
UNSAFE_RE='script-src[^;]*unsafe-inline[^;]*unsafe-eval|script-src[^;]*unsafe-eval[^;]*unsafe-inline'
WILDCARD_RE='script-src[^;]*(\*\.amazonaws\.com|\*\.cloudfront\.net|\bhttps?:\b[^;]*$|\bdata:|\bblob:)'

for f in "$@"; do
  host=$(basename "$f" .txt)
  echo "=== $host ==="
  grep -iEn "$PLACEHOLDER_RE" "$f" | sed 's/^/  placeholder: /' || true
  grep -iEn "$UNSAFE_RE" "$f" | sed 's/^/  unsafe-script-src: /' || true
  grep -iEn "$WILDCARD_RE" "$f" | sed 's/^/  wildcard-script-src: /' || true
done
```

Run via `aith assess kali exec`:

```bash
aith assess kali exec --technique INFO-DISCLOSURE \
  --intent "CSP-default-grep sweep across captured header dumps" \
  --probe-kind payload --phase recon --timeout 60 -- \
  bash /engagements/$ENGAGEMENT_KEY/tools/csp-default-grep.sh \
    /engagements/$ENGAGEMENT_KEY/scans/headers_*.txt
```

## Recording the result

Per host with a hit, record an intel-note via `aith assess record-intel note <json-file>` with:

- `title` — `CSP placeholder default surviving into production on <host>`
- `body` — the matched directive plus the placeholder literal that triggered the match
- `category` — `infrastructure`

When the matched directive directly enables an exploitable primitive (e.g., `script-src 'unsafe-inline' 'unsafe-eval'` on a page that reflects user input), record a finding via `aith assess record-finding` with the matched directive as evidence and a severity that follows the proved-impact rule — the placeholder by itself is intel; the primitive it enables is the finding.

## Production-hardening checklist cross-reference

Most vendors publish a hardening checklist that names each placeholder and the production-correct replacement. When a placeholder match fires, retrieve the vendor's hardening checklist (typically titled "Production Hardening Guide", "Security Configuration Guide", or "Deployment Hardening Checklist") and verify whether the deployment's other items in the checklist are also at default. A single placeholder match is intel; a deployment that fails three or more checklist items is an evidence pattern that the operator did not run the checklist at all.
