# Browser Semantic Evidence

Browser mode exists to answer one question: does the target behave differently
when reached by a real browser runtime than it does when reached by curl/httpx or
a plain crawler? Use it to correct evidence, not to bypass target defenses.

## Professional practice baseline

The common professional pattern is hybrid, not browser-only:

- Fast HTTP tooling (`httpx`, `curl`, `ffuf`, `nuclei`) maps cheap breadth.
- Browser-aware crawlers cover client-rendered applications and JavaScript
  request surfaces.
- A proxy-backed headed browser is kept for manual stateful flows, visual
  debugging, traffic capture, and multi-session analysis.

This matches the major tool ecosystems:

- Burp ships an embedded Chromium browser and its scanner uses browser-powered
  navigation to handle client-side technologies that a regular crawler misses:
  <https://portswigger.net/burp/documentation/desktop/tools/burps-browser> and
  <https://portswigger.net/burp/documentation/scanner/browser-powered-scanning>
- ZAP documents AJAX/Client spiders that launch browsers because modern
  JavaScript-heavy apps need browser execution, while still recommending the
  native spider for complete traditional coverage:
  <https://www.zaproxy.org/docs/desktop/addons/ajax-spider/> and
  <https://www.zaproxy.org/blog/2025-01-31-client-spider/>
- Katana supports headless and non-headless crawling for automation pipelines:
  <https://docs.projectdiscovery.io/opensource/katana/usage>
- Playwright exposes request/response monitoring, HAR, traces, screenshots, DOM
  snapshots, and console logs that are directly useful to LLM summarization:
  <https://playwright.dev/docs/network>,
  <https://playwright.dev/docs/trace-viewer>, and
  <https://playwright.dev/docs/mock>
- Chrome DevTools Protocol exposes page network events, headers, bodies, and
  timing, which is the low-level substrate behind most browser automation:
  <https://chromedevtools.github.io/devtools-protocol/tot/Network/>

The shipped typed path is `vigil assess kali browser`; it owns Playwright
execution, attribution, and bounded evidence capture. This
reference focuses on engagement decisions and evidence requirements.

## When to use browser mode

Use browser mode when a non-browser probe may be observing the edge, a fallback
page, or incomplete client state instead of the application.

### Edge or bot-management ambiguity

Trigger when curl/httpx/Katana non-headless sees a CDN/WAF interstitial, generic
access-denied body, TLS/JA3/JA4-shaped discrepancy, or a response that changes
materially when requested by a normal browser. The goal is to distinguish:

- app behavior;
- CDN/edge policy;
- runtime egress reputation;
- anti-automation or challenge page;
- a false negative caused by a non-browser TLS/client fingerprint.

If a normal headed browser reaches the app but headless does not, record the
delta and ask the operator whether the program authorizes browser-based
coverage. Do not add stealth plugins, CAPTCHA solvers, anti-detect browsers, or
unapproved proxy rotation.

### JavaScript-first or SPA behavior

Trigger when HTML is mostly a shell, routes use History API or fragments, the
app is React/Vue/Angular/Next/Svelte-style, API routes appear only after
hydration, or important links/buttons are absent from raw HTML. Browser mode
captures the requests generated by the runtime, not just the URLs written in
source.

### Suspicious universal 200s and soft errors

Trigger when many unrelated paths return the same status, size, title, or body
shape. Compare the browser's final URL, status, title, and DOM artifact with a
random-path HTTP baseline (including its body hash) so the agent does not treat
a soft error page as a valid endpoint.

### Client-side navigation and redirects

Trigger when behavior depends on `window.location`, meta refresh, fragment
routes, post-load redirects, client-side router guards, or link clicks that
construct URLs dynamically. Plain HTTP clients see only the pre-navigation
response.

### Browser-originated APIs

Trigger when useful attack surface is produced by `fetch`, XHR, WebSocket,
Server-Sent Events, GraphQL clients, gRPC-web, service workers, or background
workers. The typed runner records resource type, method, URL, and response
status. When content type or response size/hash is material, add the
metadata-only HAR or bounded body capture and derive those fields from the
artifact.

### Browser-enforced security semantics

Trigger when the vulnerability depends on what a browser enforces or ignores:

- CORS and preflight behavior;
- CSP, Trusted Types, mixed content, MIME sniffing, and X-Content-Type-Options;
- SameSite/Secure/HttpOnly cookie behavior;
- iframe and clickjacking behavior;
- DOM XSS, postMessage, BroadcastChannel, local/session storage, IndexedDB;
- download/open handling for HTML/SVG/PDF/CSV/Office preview flows.

Curl can capture headers, but it cannot prove the browser outcome.

### UI-state and viewport-specific routes

Trigger when routes or requests appear only after hover, menu expansion, scroll,
viewport breakpoints, mobile emulation, geolocation/permissions prompts, file
picker selection, drag/drop, or other user gestures. Keep the interaction set
small and record it as part of the evidence.

## Tool choice

### Default: audited headless Chromium path

For repeatable LLM-driven evidence, prefer an audited headless Chromium path
that emits bounded structured artifacts. Use Katana headless for broad
JS-aware crawling; its full crawl doctrine lives in
`agent/references/tools/recon/katana.md`.

```bash
vigil assess kali katana \
  -u https://target.example -d 3 -headless \
  -o /engagements/$ENGAGEMENT_KEY/scans/katana_headless.txt \
  --technique DISCOVERY --intent "browser-semantic crawl for JS-generated routes" \
  --probe-kind fingerprint --phase collect --timeout 1800
```

Use `--extra-args` for Katana flags the typed wrapper does not expose, after
checking `vigil assess kali katana --help` and `katana -h` in the runtime. For
example, newer Katana builds expose a system-Chrome option; only pass it when
the installed version supports it.

### Precise observation: typed Playwright runner

`vigil assess kali browser` is the typed Playwright/system-Chromium path for
deterministic, bounded browser evidence. It can capture:

- final URL, HTTP status, title, and DOM length;
- a bounded request/response event list with method, URL, resource type,
  response status, and header names;
- route candidates observed on the page, plus origins where required
  attribution was omitted;
- bounded console and page-error events;
- screenshot, DOM, and optional metadata-only HAR artifacts;
- optional bounded document/XHR/fetch body artifacts.

```bash
vigil assess kali browser https://target.example \
  --wait-selector '#app' \
  --screenshot scans/browser/target.png \
  --dom-out scans/browser/target.html \
  --har-out scans/browser/target.har \
  --technique DISCOVERY --intent "capture SPA routes and browser-only requests" \
  --probe-kind fingerprint --phase collect --timeout 180
```

Use `--steps-file` for at most 50 typed navigate/click/fill/wait/assert/eval
steps. Use `--identity` with an engagement-relative `--storage-state` artifact
for an approved authenticated flow; the command fails rather than silently
running anonymously when the identity cannot be applied. Enable bounded
document/XHR/fetch body capture only when needed with `--capture-bodies`,
`--body-dir`, and `--max-body-bytes`. Check
`vigil assess kali browser --help` before constructing a run.

### Adjacent tools

- `curl_chrome116`, when present, is useful for a browser-like HTTP/TLS/UA
  baseline. It does not execute JavaScript, maintain DOM state, or prove a
  browser-enforced outcome, so treat it as a baseline check rather than browser
  evidence.
- `vigil assess gau js-endpoints` owns static JavaScript route extraction. It
  complements browser mode by finding route strings before runtime execution.
- `jwt_tool` and SAML toolkits belong to `jwt-testing` and `saml-sso-testing`.
  Browser mode may capture tokens or redirects, but protocol manipulation is
  owned by the auth skills.
- `aem-hacker` is conditional AEM tooling. Use it after AEM fingerprints, not as
  a generic browser-semantic path.

### Headed real browser plus mitmproxy

Use a headed browser through mitmproxy when the browser itself is the
measurement instrument, not just a crawler:

- headless and headed browser behavior diverge and the delta affects coverage;
- visual state, layout, rendering, iframe behavior, or user gestures decide the
  security outcome;
- the flow needs manual observation to avoid destructive clicks or confusing
  multi-step state;
- browser extensions or profile/container separation are needed to label
  sessions or traffic sources;
- the target presents a consent page, legal notice, or non-auth challenge where
  a human must decide whether continuing is authorized;
- Burp/ZAP-style proxy history is needed as a durable request corpus.

This is still target-facing work. Start mitmproxy through `vigil mitmproxy`,
follow the engagement boundary in `agent/shared-constraints.md` §1, and register
useful captures or derived artifacts. If a challenge asks for CAPTCHA,
proof-of-human, device binding, or policy acceptance not covered by the
engagement authorization, stop and ask the operator.

## When browser mode is the wrong tool

Do not use browser mode for:

- API-only endpoints where curl/httpx already reaches the real API and no
  browser-enforced rule is under test;
- raw protocol/service checks such as DNS, nmap, TLS-only certificate work,
  SMTP, SSH, or database ports;
- high-volume fuzzing or template scanning;
- exploit payload spraying where browser prefetch/cache/retry behavior could
  create uncontrolled duplicate actions;
- cases where service workers or cache would mask server behavior unless the
  test explicitly controls cache state;
- third-party interaction outside the engagement boundary owned by
  `agent/shared-constraints.md` §1;
- CAPTCHA or anti-bot bypass attempts without explicit program approval.

## Evidence contract

Every browser-mode handoff should include:

- `trigger`: why browser semantics were needed;
- `baseline`: command-run ids for the curl/httpx/non-headless observation;
- `browser_observation`: command-run ids and artifact paths for the browser run;
- `delta`: what changed between non-browser and browser observations;
- `routes`: newly observed same-site routes and API calls;
- `soft_error_baseline`: random-path status/title/body-hash comparison when
  universal 200s or soft 404s are suspected;
- `coverage_gaps`: challenge pages, out-of-scope third-party loads, permissions,
  headless/headed mismatch, or an unavailable browser runtime.

The useful output is the delta. A screenshot alone is not evidence; pair it with
the runner's request/response metadata, relevant baseline or captured-body
hashes, and the typed interaction sequence that caused the browser to reach the
state.
