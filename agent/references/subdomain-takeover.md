# Subdomain Takeover — Claimability, Not Just the Signature

**The core lesson (learned the expensive way, twice):** a dangling-DNS "takeover
signature" is **necessary but not sufficient**. It proves a name is *unserved*; it
does **not** prove the dangling cloud resource is *re-bindable by you*. Whether a
takeover is actually claimable depends entirely on the provider's current
ownership/validation controls — which have tightened materially over the years.
**Never submit a signature-only takeover for a provider that gates re-binding; prove
it with a benign own-account claim, or research the provider's current claim
prerequisites and state the residual risk.**

Two real false positives that motivate this doc:
- **Azure (service deprecated):** a host CNAME'd to an Azure service that had been
  *deprecated*; the signature was present but the service could no longer be
  provisioned, so takeover was infeasible.
  hosts dangling to deleted CloudFront distributions, perfect signature on all 7 —
  **all 7 were non-claimable false positives** (see "CloudFront" below). Caught by an
  actual `aws cloudfront create-distribution` attempt, *before* filing.

---

## The signature (per provider) is the screening step, not the verdict

Confirm the dangling state with provider-specific discriminators (NOT mere
non-resolution — a made-up `d*.cloudfront.net` also returns NOERROR/no-A, so
target-non-resolution ALONE is not a signal):

- **CloudFront:** authoritative-NS CNAME → `d*.cloudfront.net` with no A; the target
  distribution does not resolve on 8.8.8.8/1.1.1.1 (deleted); a live CloudFront edge
  returns **TLS `handshake_failure`** when SNI = the host, and **HTTP/80 → 403 "The
  request could not be satisfied / Generated by cloudfront", `X-Cache: Error from
  cloudfront`**. Control: a live in-zone host on the same edge returns 200
  `X-Cache: Hit from cloudfront` — so the failure is alias-specific, not edge-down.
- **Azure (App Service / Traffic Manager / Blob / Cloudapp / FrontDoor):** target
  `*.azurewebsites.net` / `*.trafficmanager.net` / `*.blob.core.windows.net` /
  `*.cloudapp.azure.com` / `*.azurefd.net` returns NXDOMAIN. **Critical distinction:**
  `404 Web Site not found` / NXDOMAIN-on-the-label = *unregistered* (claimable);
  "Web App - Unavailable" / "stopped" = *provisioned-but-stopped* (owned, NOT
  claimable — signature without claimability). Always separate these.
- **Owned-parent-zone look-alikes (the #1 false alarm):** the dangling target is
  NXDOMAIN but its *parent zone* is still owned by a vendor with active SOA/NS — e.g.
  businesswire.com, secureserver.net (GoDaddy), virginmobileusa.com (Comlaude),
  bazaarvoice, FirstData, Salesforce `*.live.siteforce.com`. These are **not
  attacker-registrable** — kill them.

## Claimability by provider (the part that actually decides reward)

### CloudFront — USUALLY NOT CLAIMABLE off-zone (cert gate)
To add an *alternate domain name* (CNAME) to a CloudFront distribution you **must
attach a trusted TLS certificate whose SAN covers that exact name**. There is **no
HTTP-only / no-cert association path** anymore. The decisive API result:

```
aws --profile <yours> cloudfront create-distribution   # Aliases=[the dangling host]
=> InvalidViewerCertificate: "To add an alternate domain name (CNAME) to a CloudFront
   distribution, you must attach a trusted certificate that validates your
   authorization to use the domain name."
```

To get such a cert you must pass CA domain-control validation:
- **ACM DNS-01 / email** → requires writing the `_<token>.<host>` validation record in
  the parent zone (you don't control it) → **blocked**.
- **HTTP-01** → requires serving content at the host, which CNAMEs to a *dead*
  distribution serving nothing you control → **blocked**.

Additional AWS protections: `CNAMEAlreadyExists` blocks a name already on any
distribution (even cross-account); `AssociateAlias`/`ListConflictingAliases` (Jul
2021) re-impose cert + DNS-TXT ownership proof to move a registered alias; AWS never
reuses a deleted `d*.cloudfront.net` name (so the distribution-reissue vector is also
dead). A **deleted** source distribution is the *worse* attacker case, not the better.

**The only escape hatch:** a dangling `_acme-challenge.<host>` CNAME delegated to a
zone the attacker can register — then ACM DNS validation succeeds and the cert (hence
the claim) becomes obtainable. Check it explicitly:
```
dig +short _acme-challenge.<host> CNAME ; dig +short _acme-challenge.<host> TXT
```
Empty on both 8.8.8.8/1.1.1.1 → no delegation → CloudFront takeover is a **false
positive** regardless of how perfect the dangling signature looks.

**Triage reality:** a signature-only CloudFront takeover in 2025-26 is very likely
closed Not-Reproducible/Informational; triagers expect a served-content PoC because
the cert gate makes the bare signature unreliable.

### Azure Traffic Manager — USUALLY CLAIMABLE (no cert gate)
A Traffic Manager **profile DNS label** in `*.trafficmanager.net` is globally unique
and **re-registrable by any Azure subscriber once freed** — no certificate, no
ownership proof on the label itself. If `host.example.com` CNAMEs to a deleted
profile `<label>.trafficmanager.net`, create a profile with that relative name in your
own subscription and you control what the host resolves to:
```
az network traffic-manager profile create -g <rg> -n <label> \
   --unique-dns-name <label> --routing-method Priority --ttl 30 ...
```
Caveat (the Azure-deprecation FP): confirm the service itself is still provisionable —
a deprecated/retired Azure service may refuse creation even when the label is free.

**Caveat 2 — Azure NXDOMAIN ≠ free label (confirmed FP).** Azure can keep a deleted
Traffic Manager (or App Service) **DNS label RESERVED at the control plane** even after
the endpoint is gone and public DNS shows NXDOMAIN on 8.8.8.8/1.1.1.1. The dangling
signature then looks perfect but the label is unclaimable. ONLY a benign create attempt
settles it:
```
az network traffic-manager profile create -g <rg> -n poc --unique-dns-name <label> ...
=> (Conflict) Domain name <label>.trafficmanager.net is not available.  # RESERVED → FP
```
Always pair it with a **control create of a random label** to prove your subscription
has create permission and the pipeline works — so a `Conflict` is provably
label-specific (reserved), not a broken/blocked run.

### Other providers (brief)
- **S3:** claimable if the bucket name is free in the right region (`NoSuchBucket`
  signature); watch region pinning and global-namespace already-taken.
- **GitHub Pages / Heroku / Netlify / Surge / Shopify / Fastly / Zendesk / Tilda:**
  generally claimable by registering the app/space/store name — but many now add a
  domain-verification TXT step; verify current behavior per provider.
- **Always** confirm the dangling target's *parent zone* is not still owned before
  spending effort (the owned-parent-zone kill above).

## Methodology (operator default for this class)

1. **Screen** with the provider-specific signature (NS CNAME + no-A + provider error +
   handshake/cert behavior); kill non-resolution-only and owned-parent-zone look-alikes.
2. **Classify claimability** by provider using the rules above. For cert-gated
   providers (CloudFront), check the `_acme-challenge` escape hatch first.
3. **Prove or kill with a benign own-account claim** before submitting:
   - Use a low-cost/dev cloud profile; serve only a marker page
     (`<program> PoC - <bugcrowd-handle> - security research, no malicious content`).
   - Never intercept real traffic. Dead hosts (already 403/NXDOMAIN) serving a benign
     marker do not disrupt a live service.
   - If the claim succeeds, **leave the resource running** so triage can verify, and
     record the resource ARN/ID + a teardown command for after confirmation.
   - If the claim fails, capture the exact provider API error as kill-evidence and
     **do not submit** — it is a false positive of the protected class.
4. A genuine claim does **not** modify customer data (it creates a resource in *your*
   account) — but it IS an infra state change; coordinate with the program where rules
   require, and keep it benign.

**Chain note:** a *claimable* takeover whose origin sits under a domain that sets
non-HttpOnly, parent-domain-scoped auth/session cookies escalates from the $1,500-class
takeover to full **customer ATO (P1/P2)** — attacker JS on the taken-over origin reads
`document.cookie` and replays the bearer. The takeover claimability is the gating
precondition for the whole chain, so prove it first.
